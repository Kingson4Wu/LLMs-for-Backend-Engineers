# Harness、Agent Runtime 与 Skill：怎样让多轮任务可靠运行

工具调用让模型能提出一次外部操作；长期任务还需要决定下一步、保存已发生的事实、处理失败并在适当时停止。Harness、Agent Runtime 和 Skill 解决的是这层组织问题。它们不增加模型参数，也不把概率输出变成确定性判断；它们让模型提议、程序执行和外部状态能够在有限循环中协作。

这一章讨论的不是某个 SDK 的 API，而是一条所有多轮系统都要面对的责任链：谁组装上下文，谁执行动作，哪些状态必须保存，什么条件下恢复、升级或停止。

## 先决定是否真的需要 Agent 循环

并非只要使用模型和工具就需要 Agent。若步骤、分支和异常处理可以提前写清，例如“读取订单 → 计算金额 → 生成通知”，固定工作流通常更容易测试、观察和恢复。模型可以只负责提取字段、分类请求或生成面向用户的说明。

只有下一步必须依赖刚观察到的结果时，模型参与的循环才有意义。例如系统先查询某设备状态；发现资料缺失后决定检索另一来源；根据新的限制选择下一项检查。循环的最小形态是：

```text
任务与显式状态
  → Harness 选择本轮上下文
  → 模型提出回答或下一步
  → 程序校验、授权并执行
  → 观察结果、错误和外部状态
  → 更新状态，继续或停止
```

模型不是循环的所有者。它只能根据当前上下文生成下一步提议；运行层仍要控制回合、时间、成本、工具权限、重试和终止。把“思考—行动”写进提示词并不会自动产生这些边界。

## Harness 与 Agent Runtime 的职责不同

二者经常一起出现，但管理的范围不同。

| 层 | 主要职责 | 它不应替代的职责 |
| --- | --- | --- |
| Harness | 组装上下文、调用模型、解析结构化输出、路由工具结果 | 业务授权、长期状态和最终事实判断 |
| Agent Runtime | 保存跨轮状态，执行预算、权限、并发、恢复、审计和停止策略 | 模型的推理能力或业务系统的事务保证 |
| 工具执行器 | 以受控身份访问服务、返回观察到的结果 | 让模型决定权限或把请求当作成功 |
| 业务系统 | 保存权威状态，执行规则、事务和幂等性 | 理解自然语言任务目标 |

小型问答系统可能只需要 Harness：准备问题和资料，调用模型，返回答案。只有任务跨多轮、会产生副作用或必须中断后恢复时，才需要更完整的 Runtime。将它们拆开，不是为了制造层次，而是为了让“这次调用怎么运行”与“整个任务如何存活”分别可观察和替换。

## 把变化交给模型，把稳定路径交给程序

模型适合在信息不完整、界面变化或下一步不确定时提出候选；确定性程序适合执行已经验证、需要精确控制或带副作用的操作。长期运行系统的关键不是每一步都让模型重新规划，而是识别哪些路径已经稳定。

```text
稳定目标、约束和验收标准
            │
            ▼
可变策略：模型根据观察选择下一步
            │
            ▼
确定性执行：查询、计算、写入或已验证脚本
            │
            ▼
外部业务状态：作为成功、失败或继续的依据
```

重复任务中，已经被验证的查询、计算和操作序列应尽量固化为工作流、脚本或小而清晰的工具。模型仍可在条件变化时诊断、选择分支或请求人工处理，但不必每次重新生成同一条稳定路径。这样既减少成本和波动，也使失败更容易定位。

这不是要求把所有工作写死。环境变化快、目标开放或成功标准无法提前定义时，系统不能假装存在确定性快路径。关键是明确哪一层在适应，哪一层在保证。

## 状态、恢复与停止条件必须显式存在

模型的聊天历史不是完整任务状态。历史可能被截断、摘要或重新组装；同一事实也可能以不同措辞重复出现。Runtime 至少应保存足以恢复和审计的状态：

| 状态 | 为什么需要它 |
| --- | --- |
| 目标与验收条件 | 区分“做了动作”和“完成任务” |
| 已执行动作与幂等键 | 避免恢复后重复支付、发布或写入 |
| 关键证据与工具结果 | 让下一轮基于观察，而不是凭空重试 |
| 当前阶段与可恢复点 | 失败后知道从哪里继续 |
| 预算与限制 | 控制回合、token、时间、金额和并发 |
| 审批与权限状态 | 防止在恢复或转交时扩大原有授权 |

恢复也不是“失败后再试一次”。先要重新观察外部状态，再判断前一步是否真的未完成、已部分完成，还是已经成功但响应丢失。带副作用的工具尤其需要由业务系统提供幂等键、事务状态或可查询终态；模型的“我已经完成”不能作为恢复依据。

停止同样是运行层的责任。典型条件包括目标已由外部状态证实、证据不足、权限不足、需要人工审批、达到预算、连续失败，或出现无法安全恢复的冲突。一个会无限尝试的 Agent，不是更自主，而是缺少控制边界。

## Skill 是可按需使用的任务资产

Skill 可以把某类任务中相对稳定的知识组织起来：目标、前置条件、步骤、工具说明、脚本、示例、检查项和恢复规则。它帮助模型和宿主程序在需要时取得任务指导，因此适合重复但并非完全固定的工作。

```text
Skill
├─ 要达成什么、何时停止
├─ 可用工具与必要约束
├─ 已验证的步骤、脚本和参考资料
└─ 验收、恢复与升级规则
```

Skill 不是模型新学到的一项能力，也不是权限包。加载它只会增加这轮任务可见的说明和资源；工具执行器仍须独立验证身份、租户、额度和审批。Skill 内容也应按需提供：把所有项目手册、历史和脚本一次性塞进上下文，会重新制造上下文噪声问题。

MCP 可以帮助客户端发现外部的 prompts、resources 和 tools；Skill 则组织某项任务应如何使用这些能力。二者可以组合，但不是彼此的同义词。MCP 和领域能力模型的边界见《[从 MHS、MCP 到领域能力协议](mhs-mcp-domain-capability-protocol.md)》。

## 正确性来自外部终态与分层验证

一次 API 返回成功、一个按钮被点击、或一个工具调用没有报错，都只是过程信号。任务是否完成，应由外部业务状态和验收条件判定。例如发布操作应检查对象是否确实进入已发布状态；退款操作应检查账务记录和幂等状态；检索任务应检查结论是否被正确证据支持。

```text
模型提议
  → schema 检查：结构是否可解析
  → 策略检查：是否允许执行
  → 执行器：调用外部系统
  → 状态验证：目标是否真的达成
  → 记录轨迹：为何继续、停止或升级
```

模型自评、反思或多 Agent 互评可以提供额外信号，却不能替代这些检查。多个模型共享同一错误前提时，会共同给出流畅但错误的判断；只有独立证据、专门工具或独立验证真正增加时，多 Agent 才值得增加复杂度。

## 最小输入与最小权限是运行边界

模型服务、检索资料和工具执行器之间存在不同信任边界。向模型提供完整客户档案、内部策略或所有可用工具，未必能提高当前任务质量，却会扩大泄露、提示注入和误操作的后果。脱敏能减少直接标识，却不必然消除业务信息暴露；更稳妥的原则是只提供完成当前判断所需的最小事实和能力。

同样，工具目录不应等于模型可执行的一切。Runtime 应按用户、租户、任务阶段和风险等级缩小可见与可调用范围；高风险动作应有额度、审批、沙箱或人工确认。权限检查必须在执行侧完成，不能只写成“模型不得这样做”的提示词。

## 小结

Harness 把每轮模型调用接入上下文和工具；Agent Runtime 让跨轮状态、预算、恢复和停止成为可执行规则；Skill 沉淀可复用的任务知识和已验证路径。模型负责在不确定处提出下一步，程序负责稳定执行、最小授权和状态验证。这样，多轮系统才不会把一次流畅生成误认为一次可靠完成。如何用任务、轨迹和评分规则持续检查这条链路，见《[AI Agent Eval：从评测到业务质量系统](agent-eval-business-quality-system.md)》。
