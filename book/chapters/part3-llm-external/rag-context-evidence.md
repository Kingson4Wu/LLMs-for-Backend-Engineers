# RAG 与上下文工程：怎样把证据带入模型

模型参数来自过去的训练；一次回答需要的政策、库存、文档版本和用户权限却属于现在的外部世界。RAG 与上下文工程解决的正是这条断层：不试图把全部资料塞进提示词，而是为当前问题选出少量可信、相关且允许访问的证据。它位于模型解码之前，决定模型这一轮究竟能看见什么。

这不是“给模型加知识库”这么简单。资料被选错、过期、断章取义或越权时，模型仍可能生成流畅答案；资料选对了，也仍要检查结论是否真的由资料支持。RAG 的目标是改善证据访问和可验证性，不是把生成模型变成数据库或事实证明器。

## RAG 要补的不是参数，而是当前事实

训练会把大量资料压缩为有助于预测后续 token 的参数结构，但参数不是一份可按时间、来源、版本或权限查询的记录。政策今天更新、订单刚被取消、某份文件只对特定租户开放时，应用需要在请求时读取外部事实，而不能要求模型“从记忆里找”。

```text
已训练参数：语言规律、常见关联、任务模式
外部资料：当前版本、来源、权限、业务状态
                         │
                         ▼
问题 ──→ 检索与查询 ──→ 少量证据 ──→ 当前上下文 ──→ 模型生成
```

因此，RAG 的输入不一定是文档。它可以是产品手册的段落、数据库记录、工单状态、搜索结果、知识图谱中的关系，或一个需要由工具实时读取的数值。只要外部信息经过选择进入本轮上下文，供模型据此生成，就属于这条证据链的一部分。

## 从资料到上下文：每一步都在缩小候选范围

一个可靠的 RAG 系统不是“向量库加 LLM”，而是连续做出选择：

```text
资料源
  → 清理、版本化、切分与标注
  → 建立可查询的索引或数据访问路径
  → 根据问题召回候选
  → 权限、时间和业务条件过滤
  → 重排、去重、保留必要上下文
  → 组装证据、问题和输出要求
  → 模型生成；程序检查引用和终态
```

切分不是纯存储细节。片段过小，定义、条件和例外会分开；片段过大，真正相关的一句会被噪声淹没。资料的标题、来源、更新时间、租户、产品版本和访问范围也不是旁注，而是后续过滤和解释证据时需要的条件。

召回之后也不能立刻把前几个结果塞给模型。系统至少要问：这些资料是否允许当前用户看到？是否是目标版本？是否互相重复或冲突？哪一段最能直接支持这次结论？这些判断可以来自确定性过滤、检索模型、重排模型或业务查询；它们共同决定上下文质量。

## 检索不是只有“语义相似”一种方式

不同问题需要不同的访问路径。把所有问题都向量化，再按相似度取前几条，容易忽略精确实体、结构化条件和权限边界。

| 路径 | 擅长回答的问题 | 常见边界 |
| --- | --- | --- |
| 词项或稀疏检索 | 错误码、型号、接口名、法规条款等精确字面 | 换一种表达后可能漏召回 |
| 向量或稠密检索 | 同义表达、概念相近、问题与文档措辞不同 | 相近实体可能被混淆 |
| 结构化查询 | 库存、订单、权限、时间范围和可计算条件 | 只能回答已建模的数据关系 |
| 图或关系查询 | 明确的实体关系、多跳约束和路径问题 | 建模与维护成本较高 |

稠密表示帮助系统理解“用户没有使用资料原词时，他大概在问什么”；稀疏表示帮助系统保住“这一个错误码、版本号或产品名不能被混成另一个”。两者经常并用：先从不同路径召回候选，再按任务融合和重排。这里的“稠密与稀疏”是检索层如何选择证据，不能与 Transformer 内部的 MoE 路由或稀疏 Attention 混为一谈。

没有一种检索方式天然更高级。若问题本来就是“订单 A-17 当前是否退款”，经授权的数据库查询比从文档段落中猜测更合适；若问题是“这份政策如何理解”，带来源的文档检索更合适；若下一步取决于第一轮结果，才可能需要多轮检索与工具调用。

## 上下文工程是在有限工作区中保留决定性信息

上下文窗口大，并不意味着应把所有历史、所有文件和所有工具说明都放进去。模型只能对本轮可见 token 计算注意力；无关资料会占用长度、增加成本，并使相互矛盾的信息更难辨别。长上下文可以容纳更多证据，却不会自动完成检索、排序或事实核验。

上下文工程要回答的不是“还能放多少”，而是“为了做出这次判断，缺哪一项决定性信息”。通常可把内容分为四类：

| 内容 | 应保留什么 | 不应假定什么 |
| --- | --- | --- |
| 指令 | 目标、边界、输出形式和升级条件 | 指令能替代权限与业务规则 |
| 任务状态 | 当前输入、已完成步骤和待满足条件 | 历史越完整越有帮助 |
| 外部证据 | 与问题直接相关的原文、记录和来源信息 | 放入后模型一定会忠实使用 |
| 工具契约 | 当前确实可用的能力、参数和结果形式 | 工具清单本身等于授权 |

压缩、摘要和记忆同样是选择，不是无损存储。摘要可能遗漏限定条件；长期记忆需要在之后被检索和验证；已处理前缀的 KV Cache 只是推理计算复用，不是应用层记忆。应用应让资料的来源、时间和可信等级尽可能随证据进入上下文，而不是只留下脱离出处的结论。

## 证据链的失败通常发生在生成之前

模型“答错”常常是最终可见症状，根因可能在之前的资料链路。

| 现象 | 优先检查的原因 |
| --- | --- |
| 回答没有关键事实 | 资料未收录、切分破坏语义、查询表达不匹配或召回不足 |
| 回答引用了错误内容 | 实体混淆、版本过滤失败、重排错误或资料冲突 |
| 回答泄露不该知道的信息 | 检索阶段没有按用户、租户、资源和操作过滤 |
| 回答有引用却不受证据支持 | 模型把相邻片段、常识或猜测混入结论，引用检查不足 |
| 上下文很长但质量变差 | 噪声、重复和冲突资料挤掉了决定性证据 |

评测应分别观察这些环节，而不是只给最终回答打一个“好/坏”分数。可以检查关键资料是否被召回、是否正确过滤、最终结论是否有支持它的证据、引用是否指向正确版本，以及在资料缺失时系统是否明确说明不确定性。涉及写入、支付或发布的任务，RAG 提供的只是判断依据；真正的权限和执行结果仍要由工具和业务系统验证。

## RAG、记忆、工具与微调各补什么

这些机制都能让系统看起来“更懂”，但作用位置不同：

| 机制 | 改变什么 | 适合什么 | 不能替代什么 |
| --- | --- | --- | --- |
| RAG | 本轮可见的外部证据 | 可更新、有出处、需按权限访问的资料 | 可靠执行与事实保证 |
| 记忆 | 未来可能被选入的持久记录 | 用户偏好、任务状态、已验证结论 | 当前推理已经看见它 |
| Tool | 能读取、计算或改变的外部能力 | 实时状态、确定性计算和业务动作 | 模型对结果的正确解释 |
| 微调 | 模型参数的行为倾向 | 稳定的格式、任务模式和领域表达 | 最新私有事实或逐请求权限 |

当资料会变、需要来源和权限，优先考虑检索或查询；当结果必须由外部世界决定，优先调用工具；当行为模式本身长期稳定，才考虑训练层的适配。把它们分开，才能知道问题究竟出在模型、证据还是执行。

## 小结

RAG 的关键不是保存更多文本，而是让当前任务的决定性证据以正确的来源、版本和权限进入有限上下文。检索负责缩小候选，过滤和重排负责选择，模型负责基于证据生成，程序负责验证引用、权限和外部结果。下一章《[Function Calling 与工具调用：机制、区别与本质](function-calling-tool-use.md)》继续解释：当证据不足以回答、必须读取实时状态或执行动作时，模型的提议怎样交给外部程序。
