# LLM 怎样与外部世界交互：从生成到行动

第二部分解释了模型内部怎样把上下文变成下一个 token。模型与外部系统的连接并没有另一套魔法：应用把指令、资料、工具说明和当前状态放入上下文；模型仍然生成下一个 token；外部程序再把其中一部分输出解释为结构化数据或工具请求，执行后把结果带回下一轮。

这条链路解决的是模型的边界。模型可以写出“库存还有 24 件”，却不能仅凭这句话读到实时库存；可以生成 `refund_order` 的参数，却不能因此获得退款权限；可以说“任务完成”，却不能替代数据库、浏览器或业务系统中的最终状态。本章用一条交互链把提示词、结构化输出、工具、RAG、MCP、Skill、Harness、Agent Runtime、幻觉和评测放回各自的位置。

```text
任务、规则、资料、历史、工具契约
                 │
                 ▼
         当前上下文 / prompt
                 │
                 ▼
       LLM 解码：生成下一个 token
          │                  │
          │ 文字回答          └──→ 结构化提议 / 工具请求
          │                                  │
          ▼                                  ▼
       呈现给用户                    程序校验、授权、执行
                                             │
                                             ▼
                                  结果、错误、外部状态
                                             │
                                             └──→ 进入下一轮上下文
```

图中唯一会直接改变外部世界的是执行环境，而不是模型文本。模型负责提出下一步；应用负责决定看见什么、能做什么、是否执行、何时停止，以及怎样依据外部事实判断结果。

## 提示词与上下文：改变解码的条件，而不是给模型下程序指令

从模型角度看，系统提示、用户问题、示例、检索资料、聊天历史、工具说明和上一轮工具结果，最终都会成为当前上下文的一部分。解码器据此计算：

$$
P(\text{next token} \mid \text{current context})
$$

提示词的本质是改变这个条件。它可以说明目标、角色、边界、输出格式和优先级，使某些延续更可能；它不会修改模型参数，也不会像调用函数一样强制外部系统执行。比如“只依据下列政策回答，并给出出处”能够引导输出，但不能保证给出的资料完整、引用正确或回答没有编造。

一个可维护的上下文通常包含几类不同信息：

| 信息 | 作用 | 常见误解 |
| --- | --- | --- |
| 指令与约束 | 说明目标、禁止项、交付形式和升级条件 | 一段很长的提示词就能覆盖所有异常 |
| 用户任务 | 给出这次要解决的问题和输入 | 用户文字天然可信且无歧义 |
| 示例 | 让模型看到期望的判断或格式 | 示例越多越好 |
| 事实与状态 | 提供当前资料、工具结果、会话状态 | 放进上下文就自动成为真相 |
| 工具契约 | 说明有哪些操作、参数和返回值 | 声明工具等于授予模型权限 |

上下文是有限的工作区，不是无限记忆。无关历史、重复资料和过多相似工具会挤占注意力，也会让模型更难找到真正决定答案的证据。所谓**上下文工程**，就是为每一次调用选择足够、相关、来源明确的 token，而不是不断往 prompt 里累积内容。[Anthropic 对上下文工程的讨论](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)强调的也是这种有限注意力下的选择问题。

这也解释了提示注入的危险：从网页、邮件、文档或工具返回的文本，可能包含“忽略之前规则”之类的内容。它对模型来说仍是上下文的一部分。应用不能只要求模型“不要相信它”，还应区分可信指令与不可信数据，并在执行前由程序检查权限、参数和目标。

## 结构化输出：把生成的提议交给程序

自由文本适合解释，却不适合让程序稳定地读取和分支。结构化输出要求模型生成符合约定形状的数据，例如分类结果、提取字段、SQL 候选、界面状态，或工具调用参数：

```json
{
  "action": "lookup_inventory",
  "warehouse": "SZ-01",
  "sku": "water-500ml"
}
```

这仍是解码。区别在于，某些接口可以在生成阶段约束可选 token，使输出符合 JSON Schema 等语法约束；也可以在生成后由解析器拒绝无效结果。两者都只能把保证限定为“字段、类型和嵌套关系符合约定”；[Structured Outputs 文档](https://platform.openai.com/docs/guides/structured-outputs)也将其描述为 schema adherence，而不是事实正确性。

生成期约束的机制是：系统跟踪当前前缀对应的语法或 schema 状态，屏蔽不可能把这个前缀延续为合法结构的 token，再从剩余候选中继续解码：

```text
模型 logits → 语法 / schema 状态 → 合法 token 掩码 → 选择下一个 token
```

这比事后解析更早地排除格式不可能成立的路径，却不能使字段含义、事实或业务权限自动正确。schema 过严、tokenizer 与语法约束无法衔接，或服务根本不支持该约束时，应用应明确选择报错、重试或降级；不能假定存在通用的静默回退。

从模型字符串到真实业务动作之间，至少隔着四层判断：

```text
模型输出
  → 语法与结构：能否解析，字段是否齐全、类型是否正确
  → 语义与业务：选的是不是正确订单，金额和状态是否合理
  → 授权与策略：当前用户能否执行，该动作是否需要审批
  → 执行与结果：下游系统是否真正完成，最终状态是否满足目标
```

`{"order_id":"A-17","amount":100}` 即使是合法 JSON，也可能指向错误订单、超过额度，或在已退款后重复提交。结构化输出的价值不是让模型“更懂业务”，而是建立模型提议与确定性检查之间的接口。它是工具调用的基础，也常常已经足够解决抽取、路由和表单填充等任务，不必为了有 Agent 而增加循环。

## 工具调用：模型提出请求，程序访问外部世界

工具是由应用提供的可执行能力，通常用名称、描述、参数 schema 和返回格式构成契约。例如 `get_inventory(sku, warehouse)` 可以读取库存，`create_refund(order_id, amount)` 可以提出退款操作。模型在当前上下文中生成符合契约的调用提议；宿主程序验证并实际调用服务；结果或错误以新的消息进入后续上下文。

```text
用户：深圳仓还有多少 500ml 矿泉水？
应用 → 模型：问题 + get_inventory 的说明与 schema
模型 → 应用：get_inventory({"sku":"water-500ml", "warehouse":"SZ-01"})
应用 → 库存服务：经认证的实际请求
库存服务 → 应用：{ "available": 24, "as_of": "10:32" }
应用 → 模型：工具结果
模型 → 用户：深圳仓目前可用库存为 24 件（10:32）。
```

因此，函数调用不是模型直接调用函数，而是一种结构化输出协议。模型不能自己打开数据库连接，也不能绕过服务端的身份、租户隔离、幂等性和审计。工具结果也不等于任务完成：请求可能超时、返回空值、只完成部分操作，或遇到竞争状态；下一轮应看到实际结果，而不是把“已发起调用”写成“已经完成”。

工具大致可分为读取、计算和产生副作用三类。读取工具仍要考虑数据范围和新鲜度；计算工具需要输入和单位校验；写入、支付、删除、发布等副作用工具则需要更严格的权限、限额、幂等键、审批或人工确认。工具说明必须清楚且边界小：若人也无法判断两个工具该用哪一个，模型更不可能稳定判断。工具的名称和描述是模型的接口，认证与执行策略则属于程序的接口。

## 多轮交互：固定工作流与 Agent 循环的分界

单次工具调用已经是“模型—外部系统”交互，但它未必是 Agent。若步骤和分支可以预先确定，例如“查库存 → 计算总数 → 生成答复”，程序应使用固定工作流：它更容易测试、观察和恢复。固定工作流也不等于只有一条直线：提示词链把已知子任务依次拆开；路由先分类再走不同分支；互不依赖的工作可以并行；生成—评审—改写只在评价标准清楚时才值得循环。它们都由程序规定控制流。

当下一步必须根据刚获得的结果决定时，模型才开始参与控制循环。例如商品未找到时，模型可能先查目录；发现单位为托盘后再查包装规格；最后根据库存、运输限制和用户目标选择下一步。这里的本质不是多写几段 prompt，而是**观察改变下一次输入，下一次解码再选择动作**。

```text
任务与状态 → 组装上下文 → 模型提议下一步
      ▲                              │
      │                              ▼
更新状态 ← 结果、错误、环境观察 ← 校验并执行工具
      │
      └── 达成目标 / 无法继续 / 超过预算 / 需要审批时停止
```

[ReAct](https://arxiv.org/abs/2210.03629)研究了把推理轨迹与环境动作交替进行的方式。值得保留的是反馈改变后续行动这一机制，而不是把“思考—行动”文本模板当成所有 Agent 的定义。所谓反思、重试、评审或自我修正，同样只是将新观察放入下一轮上下文再解码；除非训练过程真的更新了参数，它们不是模型在运行时“学会了”。

循环会积累成本、延迟和错误，也可能重复调用或在两个计划之间振荡。因此，状态需要显式记录目标、已做动作、关键证据、待满足条件、资源消耗和可恢复点；停止条件也必须由运行层检查。多 Agent 只在带来独立信息、专门工具、真正可并行的子任务或独立验证时才有意义。把同一个错误前提分发给多个角色，只会增加调用和摘要损失。

## 资料、记忆与 RAG：把需要的证据选入这一轮

模型参数保存的是训练中形成的统计规律，不是可按版本、权限和时间查询的业务知识。**RAG**（retrieval-augmented generation）将检索到的外部资料作为当前上下文，让生成以这些资料为条件；原始 [RAG 论文](https://arxiv.org/abs/2005.11401)将参数化模型与可检索的非参数化记忆结合，正是为了解决知识更新、来源和精确访问的问题。

典型链路是“问题 → 检索或查询 → 选出片段/记录 → 放入上下文 → 生成带依据的答复”。向量检索只是其中一种召回办法；关键词、SQL、知识图谱、权限过滤和重排序也都可能更适合。RAG 的关键不是“有向量库”，而是让与这次问题相关、可访问、版本正确的证据进入模型可见的上下文。

| 概念 | 它是什么 | 它不保证什么 |
| --- | --- | --- |
| 上下文 | 本次推理实际看见的 token | 会在下一轮自动保留 |
| 记忆 | 应用持久化后、未来可选择读取的记录 | 已经影响当前模型 |
| RAG | 为当前问题检索并提供外部资料的过程 | 检索完整、资料正确或模型忠实引用 |
| KV Cache | 已处理前缀的推理计算复用 | 用户偏好或长期业务记忆 |

幻觉并不是只发生在“模型不知道资料”时。模型的目标是生成合乎上下文的延续，不是自动证明每一句话为真；检索错误、资料过期、上下文冲突、引用与结论脱节，都可能得到流畅但错误的答案。对事实任务，应要求来源、检查结论能否由证据支持，并在关键场景用工具或规则验证。RAG 是补充和约束证据的机制，不是事实保证器。

《[RAG 与上下文工程：怎样把证据带入模型](rag-context-evidence.md)》继续说明资料如何经过切分、召回、过滤、重排和压缩，成为本轮上下文。

## MCP、Skill、Harness 与 Agent Runtime：它们在链路中的位置

这些名称常被并列，实际职责不同：

| 名称 | 位于哪里 | 它解决什么 | 它不解决什么 |
| --- | --- | --- | --- |
| Tool | 模型提议与执行器之间 | 定义一项可调用能力及其输入输出 | 是否获准、是否成功、任务是否完成 |
| MCP | 客户端与外部能力之间 | 约定怎样发现和使用 prompts、resources、tools | 业务授权决策、控制流程和结果正确性 |
| Skill | 任务知识进入上下文之前 | 打包某类任务的说明、脚本和资源 | 更新模型参数或自动安全执行脚本 |
| Harness | 每次模型调用周围 | 组装上下文、调用模型、路由工具结果 | 取代业务系统的权限和事实判断 |
| Agent Runtime | 整个多轮任务周围 | 保存状态、策略、预算、恢复、审计与停止 | 让模型输出天然可信 |

[MCP 规范](https://modelcontextprotocol.io/specification/draft/server/index)将 prompts、resources、tools 作为服务器提供给客户端的不同原语：prompt 是可选用的任务模板，resource 是应用可提供的上下文资料，tool 是模型可以提议调用的能力。MCP 也可以协商认证与授权所需的协议能力；但令牌或已建立的身份仍不等于业务允许某位用户对某个资源执行某种动作。客户端和业务服务仍须按用户、租户、资源和操作决定可见范围与执行条件。

Skill 更接近按需加载的任务手册：它把指令、工作流、脚本和资源组织在一起，帮助模型和宿主程序处理一类任务。它可能通过 MCP 分发，也可能来自文件、代码仓库或产品内置配置；无论来源如何，Skill 改变的是当前任务可获得的指导和资源，不是模型参数。

Harness 是围绕一次或一串模型调用的控制程序；它选择上下文，发送请求，接收结构化输出，调用执行器，把观察写回状态。Agent Runtime 则是更广的运行层，负责跨轮状态、预算、权限策略、并发任务、恢复和可追溯轨迹。一个简单的问答应用可能只有 prompt 与结构化输出；只有在任务需要根据反馈继续行动时，才需要完整的 Harness 和 Agent Runtime。模型服务怎样排队、批处理并在 GPU 上执行，则属于[第四部分：LLM 基础设施](../part4-serving-runtime/llm-infrastructure.md)。

《[Harness、Agent Runtime 与 Skill：怎样让多轮任务可靠运行](harness-runtime-skills.md)》继续解释多轮状态、确定性执行、失败恢复和业务终态验证怎样协作。

## 可靠性来自可验证的闭环，而不是更长的提示词

可靠系统把每一层能够验证的事情交给对应层：schema 验证结构，业务规则验证含义与权限，执行器返回实际结果，外部状态验证目标，评测检验系统在一组代表性任务上的表现。提示词、模型自评和“请仔细检查”可以提供信号，却不应替代这些控制。Guardrail 也不是单一模型：输入过滤、输出检查、工具参数校验、沙箱、限额、批准和审计分别保护不同的入口与后果。

**评测**不是在某一次请求中让模型给自己打分，而是用固定任务、输入版本、允许工具和评分规则反复检验系统。它至少应分别观察：

| 维度 | 例子 |
| --- | --- |
| 最终结果 | 订单是否真的创建，答案是否有可支持的来源 |
| 过程质量 | 是否选择正确工具，是否处理超时、空结果和拒绝访问 |
| 安全与副作用 | 是否越权、重复退款、泄露不该读取的数据 |
| 成本与时延 | 调用轮数、token、工具次数和完成时间是否在预算内 |

对多轮系统，最终环境状态往往比“模型说已完成”更重要。轨迹应记录输入版本、模型与策略选择、工具调用、返回结果和最终判定，才能复现失败并比较改动。[Anthropic 对 Agent eval 的说明](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)也将评测定义为给定输入、以评分逻辑衡量系统输出和行为的测试。

回到全书主线：提示词、RAG 和 Skill 决定模型这一轮看见什么；结构化输出和工具调用把生成变成程序可处理的提议；Harness 与运行时把提议和外部结果组织成有限、可停止的循环；授权、执行器和评测则负责验证现实中发生了什么。理解这条责任链，就不必把任何一个框架名词误认为 Agent 的全部本质。
