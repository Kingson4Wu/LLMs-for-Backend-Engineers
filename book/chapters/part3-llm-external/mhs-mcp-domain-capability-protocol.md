# 从 MHS、MCP 到领域能力协议

Anthropic 在 2026 年 8 月 27 日发布了 MHS（Model Hardware Standard）的 research preview。按照官方定义，MHS 是一个让 AI Agent 安全操作物理设备的共享规范，第一批面向科学实验室和先进制造场景。它现在还不是一个成熟的公共标准，而是先开放给一部分合作方试用，官方也明确说是在开源之前先做安全评估和最佳实践探索。

MHS 首先是硬件标准。但它背后的工程问题并不新：当一个领域里有大量异构实现时，如何把对象、能力、状态、约束和操作方式抽象成统一模型，让上层软件可以稳定使用。

这个需求不是 AI 发明的。AI 出现之前，软件工程里已经有很多类似抽象：

- JDBC 抽象不同数据库；
- POSIX 抽象不同操作系统能力；
- USB Class 抽象不同设备类别；
- Kubernetes 抽象底层计算资源；
- OpenAPI 把服务接口描述成机器可读契约。

MHS 的特殊之处在于，它把这类标准化抽象放到了“物理设备 + Agent 使用”的场景里。AI 没有创造这个需求，但 AI 改变了使用者，也放大了这个需求。

这类标准本质上是为了减少重复适配，并把隐性知识变成公共契约。没有标准时，每个业务系统、每个 Agent、每个工具接入方都可能要重新理解厂商接口、说明书、状态语义和安全边界。标准化以后，这些领域知识可以沉到一个公共抽象层里，上层尽量面向稳定的对象和能力编排任务。

对 Agent 来说，这还有一个很实际的附加好处：当 MHS 通过 MCP、CLI、code files / APIs 或更上层的业务 API 被访问时，上层接入层不需要反复描述完整的硬件说明书。MCP Tool 可以把说明主要集中在业务入口和参数上，设备能力、状态、单位、安全限制这些更稳定的内容，则从 MHS 的标准设备表示里读取。这样能减少上下文里反复携带厂商说明、临时提示词和长段规则说明的成本。

## MHS 标准化的对象

MHS 官方定位是硬件标准。它面向的是显微镜、移液工作站、机械臂、传感器、激光系统等有可编程接口的物理设备。

它要解决的不是“AI 能不能调用一个函数”，而是更底层的集成问题：

![MHS 要解决的硬件集成问题：大量设备供应商、能力相似但接口不同、说明书和安全限制分散，导致人工适配成本高，Agent 还需要动态理解和组合](../../assets/zh/posts/20260831-mhs-mcp-domain-capability-protocol/mhs-integration-pain.svg)

*MHS 要处理的不是单个函数调用，而是硬件语义分散、供应商接口不同和重复适配的问题。*

MHS 的做法是引入标准化 Driver。这个 Driver 位于厂商接口和上层 Agent 之间。它不是替代设备厂商的底层协议，而是把厂商 SDK、设备接口和硬件状态翻译成上层可以稳定理解的表示：

![MHS Driver 位于物理设备、厂商 SDK、标准设备表示和上层 Agent 或程序之间](../../assets/zh/posts/20260831-mhs-mcp-domain-capability-protocol/mhs-driver-stack.svg)

*MHS Driver 的作用是把厂商 SDK 和设备接口翻译成上层可以稳定使用的设备表示。*

MHS Driver 使用简单 primitive，例如 `read` 和 `write`。官方举的例子是：

![MHS Driver 的 read 和 write primitive：read 用于 get temperature，write 用于 set temperature](../../assets/zh/posts/20260831-mhs-mcp-domain-capability-protocol/mhs-read-write.svg)

*`read` 和 `write` 本身很简单，关键仍然是它们背后的设备语义、状态和安全约束。*

这看起来像接口统一，但更关键的是设备表示统一。

一台设备不只是几个函数。它还有很多从代码里看不出来的信息：

- 能测什么；
- 能调什么；
- 当前状态是什么；
- 物理特性是什么；
- 安全限制是什么；
- 哪些操作需要人确认；
- 出错后能不能恢复。

Anthropic 官方文章提到，很多信息过去存在纸质说明书、用户电脑文件，或者人的经验里。MHS Driver 可以通过 tags 让用户用自然语言写入这些信息，也可以让 Agent 通过访谈方式收集硬件设置，然后生成 reference file，描述设备能测什么、能调什么、会执行哪些安全限制。

所以 MHS 的关键不是给硬件包一层 API，而是把硬件说明书、厂商接口、设备状态、物理特性和安全限制，变成 Agent 可以读取和使用的结构化设备表示。

这也解释了为什么它不只是“方便调用”。如果没有这层结构化表示，业务方即使通过 MCP 暴露硬件工具，也常常要在 tool description、prompt 或额外文档里反复解释设备说明、厂商差异、单位换算和安全规则。标准化之后，这些内容可以作为设备模型的一部分被查询和复用，上层 MCP Tool 可以主要保留和当前业务任务直接相关的说明。

例如不同机械臂厂商可能提供不同接口。上层更需要的是统一的设备能力模型，而不是这些厂商函数名：

![不同机械臂厂商接口被抽象成统一 RobotArm 能力模型，包括 move、grasp、position、load、workspace 和 safety limits](../../assets/zh/posts/20260831-mhs-mcp-domain-capability-protocol/hardware-capability-model.svg)

*标准化的重点不是让函数名看起来一样，而是让设备能力、状态和约束有共同语义。*

设备表示统一以后，上层才有可能做多设备编排。Agent 可以读取各个设备的运行状态，按照实验或生产流程安排步骤，监控结果变化，并在条件变化时调整参数。对于长时间运行或需要稳定执行的任务，Agent 也可以把一组设备命令写成确定性脚本，让设备按脚本执行，而不是每一步都依赖模型在线推理。

边界也要说清楚。MHS 目前仍是 research preview，官方当前描述的是具备可编程接口的设备。它降低的是集成、发现、描述和编排成本，不代表 Agent 已经具备完整的物理世界理解能力，也不代表真实硬件排障可以脱离专家。

## MCP 和 MHS 的分层关系

MCP（Model Context Protocol）是 Anthropic 在 2024 年 11 月开源的标准。官方定义里，MCP 是一个把 AI assistant 连接到外部系统的开放标准，外部系统包括内容仓库、业务工具、开发环境、数据源、工具和工作流。

MCP 的结构大概是：

![MCP 的基本结构：MCP Client 通过 MCP Server 连接 Data、Tool 和 Workflow](../../assets/zh/posts/20260831-mhs-mcp-domain-capability-protocol/mcp-basic-shape.svg)

*MCP 解决的是 AI 应用如何连接外部系统，并发现和使用数据源、工具与工作流。*

本文重点讨论其中的 Tool，因为 MHS 接到 Agent 时，最容易和 MCP Tool 混在一起。

当前 MCP 规范里的 Tool 会有 `name`、`description`、`inputSchema`，也可以有 `outputSchema`；工具结果可以是文本、图片、音频、资源链接，也可以包含 `structuredContent`。

所以 MCP 不是只能暴露非结构化自然语言。它可以承载自然语言描述，也可以承载结构化 schema 和结构化结果。

但 MCP 不负责替具体领域建立领域模型。它可以告诉 Agent：

- 这里有一个 tool；
- 这个 tool 叫什么；
- 参数 schema 是什么；
- 调用结果是什么。

它不会天然告诉 Agent：

- 显微镜应该有哪些状态；
- 移液工作站有哪些安全限制；
- 离心机的转速和离心力如何换算；
- 机械臂的工作空间和负载边界是什么。

这些属于 MHS 要解决的问题。

两者的关系更适合这样理解：

![MCP 与 MHS 的分层关系：AI Agent 通过 MCP、CLI、code files 或业务 API 访问 MHS，MHS 再通过 Driver 连接具体硬件](../../assets/zh/posts/20260831-mhs-mcp-domain-capability-protocol/mcp-mhs-layering.svg)

*MCP 是 Agent 接入外部系统的一种入口；MHS 位于更底层，负责把硬件设备表示成可发现、可读取、可约束的能力模型。*

MHS 是 model-agnostic 的。官方资料里也提到，agent harness 可以通过标准协议访问 MHS，例如 MCP；也可以通过命令行接口和 code files（APIs）控制硬件。

因此，MCP 是 Agent 连接外部系统的协议层；MHS 是物理设备标准化表示和控制的设备层。MCP 可以成为访问 MHS 的入口，但 MHS 主要解决设备发现、标准化 Driver、状态读写、设备参考文件和安全约束这些问题。

## MHS 不替业务方设计工具

这里还要区分“硬件标准层”和“业务接入层”。

MHS 提供的是硬件侧的标准能力层。它让不同厂商设备用相对一致的方式暴露状态、能力、限制和读写操作。但具体业务如何把这些能力暴露给 Agent，仍然由使用方自己决定。

一个实验室可以在 MHS 之上封装 MCP Server，把实验任务暴露成工具；也可以写 CLI 命令，让自动化脚本调用；还可以写 code files（APIs），把 MHS 作为底层设备控制层。MHS 不替业务方决定工具名、参数设计、提示词说明、审批流程和任务编排方式。

更合理的集成关系是：

![业务目标通过业务方自己的 MCP Tools、CLI、code files 或 APIs 接入 MHS 标准设备表示，再连接不同厂商设备 Driver 和具体硬件](../../assets/zh/posts/20260831-mhs-mcp-domain-capability-protocol/business-access-stack.svg)

*业务方设计上层工具和流程，MHS 负责让底层硬件能力更稳定地被替换和复用。*

这样分层以后，业务方可以根据自身需求定义上层工具。例如同样是显微镜，科研实验可能暴露 `capture_cell_image`，质检系统可能暴露 `inspect_surface_defect`。这两个工具的业务含义不同，但底层都可以依赖 MHS 提供的标准设备能力。

MHS 的好处也在这里。当底层硬件从 Nikon 换成 Leica，或者机械臂从 ABB 换成 KUKA，只要新的设备 Driver 能提供同样的标准能力，上层实验流程、MCP Tool、CLI 或业务代码就有机会保持稳定，不必跟着底层厂商接口重写。多设备场景下，Agent 或业务程序也可以基于 MHS 的设备发现和状态描述，找到可用设备并做适配，而不是每次都重新读一遍厂商说明书。

## 只用 MCP 能不能满足领域需求

只用 MCP 也能做很多事。

比如一个团队可以直接写一个 MCP Server，把显微镜、机械臂或离心机暴露成工具：

```text
microscope.capture_image()
microscope.set_focus()
robot.move_plate()
centrifuge.spin()
```

从“Agent 能不能调用硬件”这个角度看，这条路是可行的。MCP 本来就可以连接外部工具和系统，只要硬件背后有可编程接口，就可以由 MCP Server 包装出来。

在固定场景里，这甚至可能是更务实的做法。比如只接一台显微镜，只服务一个实验流程，设备也不会频繁替换，那就没有必要先设计一套完整 MHS 式模型。写一个 MCP Server，把需要的能力暴露出来，业务可以跑通。

问题在于，这样做主要解决调用入口，没有自动解决领域语义标准化。

如果没有 MHS，每个 MCP Server 都要自己决定：

- 设备叫什么；
- 能力怎么命名；
- 状态怎么表达；
- 参数单位是什么；
- 安全限制放在哪里；
- 错误如何分类；
- 哪些操作需要人确认；
- 多个设备如何互相发现和协作。

结果很可能是每个团队都做出一套自己的“硬件 MCP”。表面上 Agent 都能调用工具，实际上工具背后的设备模型、状态语义、安全约束各不相同。Agent 换一个实验室、换一批设备、换一个供应商，就又要重新理解一遍。

所以问题不是“没有 MHS 能不能做”，而是“只靠 MCP 做出来的东西能不能跨设备、跨供应商、跨实验室复用”。MCP 负责让 Agent 接触到能力；MHS 负责让硬件能力本身有共同语义。

这也是判断标准化是否必要的边界：一次性集成看调用入口，长期复用看领域模型。MCP 足够解决“接上去”；MHS 试图解决“接上去以后，各种设备能不能用同一种语义被理解和编排”。

## AI 放大的是领域语义需求

设备标准化、驱动抽象、协议统一，在 AI 出现之前就存在。工业自动化、机器人、IoT、USB Device Class、OPC UA 都在处理类似问题。

AI 带来的变化是使用者变了。

过去是程序员提前知道现场有哪些设备，提前读说明书，提前写适配代码：

```python
microscope.capture()
```

这种模式里，很多语义存在程序员脑子里。程序员知道这个函数代表什么，知道参数范围，知道什么情况下危险，知道失败后应该怎么处理。

Agent 模式不同。Agent 面对的是更动态的环境。它可能不知道现场有什么设备，也不知道每台设备的厂商接口。它需要自己发现设备、理解能力、判断限制、组合动作。

比如用户只说：

> 完成一个实验。

Agent 需要知道：

- 有哪些设备；
- 哪个设备可以拍摄；
- 哪个设备可以加液；
- 哪个设备可以离心；
- 参数范围是什么；
- 安全边界是什么；
- 执行顺序是什么；
- 失败后能否恢复。

所以 AI 放大的不是“多几个 API”这个需求，而是“机器必须理解能力语义”这个需求。

MHS 的价值正是在这里。它把过去由人读说明书、写适配、记经验的部分，尽量转成结构化、可发现、可组合、可约束的模型。Agent 不再只是拿到一个函数，而是拿到一个带语义边界的能力。

## 从硬件能力到领域能力

如果只停在硬件层，MHS 是一个物理设备标准。但从工程抽象看，它可以被理解成一种特殊的通用业务标准化：针对某个领域，把稳定对象、通用能力、状态变化、约束规则和执行动作抽象出来。

这里的“业务”不是狭义的企业管理系统，而是一个领域里反复出现、可以被抽象和复用的工作模式。实验室自动化就是一种业务。制造现场也是一种业务。它们都有稳定对象、流程和约束：

- 对象：设备、样本、工单、物料、实验、产线；
- 能力：测量、移动、加液、加工、检测、回滚；
- 状态：空闲、运行中、失败、完成、待确认；
- 约束：安全、容量、权限、物理边界、工艺要求；
- 流程：计划、执行、监控、调整、验证。

MHS 的官方范围是硬件，但它给出的抽象方式可以往外看：

![从现实世界业务领域到领域模型、能力模型、标准化 Adapter 或 Driver，再到软件、硬件、服务和人](../../assets/zh/posts/20260831-mhs-mcp-domain-capability-protocol/domain-capability-layers.svg)

*把硬件领域的做法往外看，就会回到领域模型、能力模型和标准化适配层这些老问题。*

把 MHS 往外推，不是说“业务领域比硬件高一层”，而是说硬件只是一个领域。未来如果有类似标准，更可能表现为智能家居、支付、游戏、制造、物流、医疗、能源这些领域各自的能力模型，和硬件领域平级。

这类标准要解决的核心问题还是一样：一个领域里有很多异构实现，上层业务不应该直接绑死在某个厂商接口上。标准层要把稳定的对象、能力、状态和约束抽出来，让不同实现可以被同一种语义理解和替换。

支付行业就是一个容易理解的例子。支付宝、微信支付、Stripe、Apple Pay、银行卡通道，看起来都是“收款”，但接入机制、签名方式、授权流程、异步通知、退款、对账、风控字段都不一样。今天一个电商系统要支持多种支付方式，通常要在支付网关或业务代码里做很多适配。

如果把这个思路类比成一个假设的 Model Payment Standard，重点不是让 Agent 绕过业务规则直接发起扣款、退款等动作，而是把支付领域里相对稳定的对象、能力和约束抽出来。如果叫 Model Finance Standard，范围会更大，还会涉及账户、资产、授信、风控、清结算等更多对象，支付只是其中一部分。

这样上层 AI 电商、客服 Agent 或运营系统关心的是“创建支付单”“查询支付状态”“发起退款”“对账异常处理”这些业务语义，以及每个动作需要满足的确认、权限、风控和合规条件。底层到底是支付宝、微信支付，还是海外信用卡通道，由 Adapter 处理。换支付方式时，上层流程就有机会保持稳定。

游戏平台也是类似问题。Steam、PlayStation、Xbox、App Store、Google Play 或不同游戏发行平台，都可能涉及账号、支付、库存、成就、订阅、退款、反作弊、家长控制等能力。这里更准确地说，是假设有一个面向游戏平台服务的标准，而不是统一游戏玩法或游戏引擎。它的重点也不是统一几个 API 名字，而是把这些平台服务抽象成稳定对象和能力：

这些名字都只是为了说明抽象方向，不是说已经有这样的官方标准。这里要说明的是：当一个领域存在大量异构实现、类似能力、频繁替换和组合，上层又希望 Agent 或业务系统快速接入时，就可能出现类似 MHS 的标准化诉求。

智能家居也可以放在同一类里看。一个家庭里可能同时有不同厂商的灯、门锁、空调、摄像头、窗帘、传感器，也可能接入 HomeKit、米家、Google Home、Home Assistant 这类平台。用户真正关心的不是“调用某个灯泡 API”，而是“我回家了”“我要睡觉了”“家里没人了”“发现异常移动”这些场景。这里需要统一理解的是房间、人员、设备、传感器、占用状态、权限、安全和隐私约束。底层设备来自哪个厂商，可以交给 Adapter 或 Driver 处理；上层关心的是场景目标和动作组合。

![支付、游戏平台服务和智能家居的领域能力模型类比，展示对象、能力、约束和异构实现](../../assets/zh/posts/20260831-mhs-mcp-domain-capability-protocol/domain-examples.svg)

*支付、游戏平台服务和智能家居只是类比，用来说明其他领域也可能出现类似的能力模型和标准化适配层。*

是否值得做这种标准，关键看五件事：

- 异构实现是否足够多；
- 对象和能力是否相对稳定；
- 是否需要频繁替换和组合；
- Agent 是否需要动态理解；
- 共同模型的收益是否大于迁移成本。

这里最容易犯的错误，是只统一接口，不统一语义。看起来大家都叫 `set_mode`，但一个平台的“离家模式”只是关灯，另一个平台还会锁门、打开摄像头、降低空调功率、启动告警规则。上层 Agent 看到同一个动作名，并不代表它们有同一个语义。

有价值的标准化，要抽象到业务对象和能力语义，而不是停留在函数名。

## 小结

MCP 和 MHS 的区别可以这样总结：

- MCP 是 AI 应用连接外部系统的协议，覆盖数据源、工具和工作流；
- MCP 既可以承载自然语言描述，也可以承载结构化 schema 和结构化结果；
- MHS 是让 AI Agent 安全操作物理设备的共享规范；
- MHS 的核心是标准化 Driver、read/write primitive、设备发现、设备参考文件和安全约束；
- MHS 可以通过 MCP、CLI 或 code files / APIs 被 Agent 访问；
- 具体如何暴露工具、命令和业务流程，由使用方基于自己的场景设计，MHS 负责让底层硬件能力更稳定地被替换和复用。

总结成几条：

- MHS 的官方定位是硬件标准；从工程本质看，它也是一个领域能力标准化案例。
- 在硬件设备这个领域里，MHS 把设备对象、能力、状态、约束和操作方式抽象成统一模型，让不同厂商、不同型号的设备可以被软件和 AI Agent 以相对一致的方式理解、替换和调用。
- 这种标准化需求不是 AI 发明的。异构系统集成、厂商适配、接口标准化、领域模型抽象，一直都是软件工程和工业系统里的老问题。
- AI 改变的是使用者和使用方式。Agent 不再满足于调用写死的 API，而是需要在动态环境中发现能力、理解语义、读取结构化约束、组合资源、完成目标，所以语义暴露和结构化描述的需求被放大了。
- 这是一种特定领域的通用标准化，主要目的不是概念统一，而是复用：复用领域模型、复用接入层、复用业务流程，减少每次换厂商、换设备、换平台时的重复适配。
- MCP 和 MHS 是不同层次的东西。MCP 解决 Agent 如何连接外部系统；MHS 解决硬件设备如何被标准化描述和控制。MHS 可以通过 MCP 暴露给 Agent，也可以通过 CLI、code files / APIs 等方式被访问。
- 这个思路进一步推广到其他领域，就变成了领域能力模型或领域能力协议的问题。支付、游戏、智能家居、制造、物流、医疗、能源等领域，如果也存在大量异构实现和重复接入成本，后续都可能出现类似的标准化抽象。
- 这类工程做法并不新：当接入需求变多、替换需求变多、复用价值变大时，行业就会倾向于在某一层增加标准。AI 加速了这个过程，也让标准不再只描述接口，还要描述对象、能力、状态、约束和语义边界。

落到工程上，就是一句很普通的话：当一个领域的接入方足够多、实现差异足够大、替换和组合需求足够强时，就值得考虑在中间加一层标准化抽象。AI Agent 只是让这件事更明显，因为它需要的不只是接口，还需要可读取、可约束、可复用的领域语义。

这件事的难点也不在字段设计，而在共同语义。只有当一个领域的对象足够稳定、能力足够通用、异构实现足够多、组合需求足够强时，领域能力协议才有实际价值。
