# 多语言大模型：不同语言怎样共享表示与能力

中文提问时，模型会不会先把问题翻成英语、推理后再翻回来？对常见的端到端多语言 LLM，通常不会存在一条可指认的“中文文本 → 英文文本 → 中文文本”内部流水线。模型把输入切成 token，用同一组参数计算下一 token 的分布；模型内部的状态是连续向量，不能直接等同于某一种自然语言的句子。

这不意味着语言差异已经消失。训练数据、tokenizer、模型规模、后训练和任务类型共同决定一种语言的实际能力。本章解释共享从哪里来，以及为什么不能把它误解成“所有语言天然等价”。

## 从字符到共享模型

```text
不同书写系统 → tokenizer → token 向量 → 共享 Transformer 层
                                      ↓
                              词表上的下一个 token 分布
```

多语言训练把多种语言的材料放进同一训练目标中。模型不需要先把每个样本翻译成英语；它直接在各语言 token 序列上预测后续 token。共享参数会让不同语言竞争同一表示能力，同时也允许某些可复用的模式——例如实体关系、代码结构、常见问答形式——在语言之间迁移。

“共享表示空间”是有用的概括，但不应理解为每个意思都有一条语言中立的固定向量。表示会随上下文、层数、位置和任务变化；模型也可以保留与语言、脚本或文体有关的特征。

## 跨语言对齐从哪里来

对齐通常来自几种相互补充的信号：

| 信号 | 它提供什么 |
| --- | --- |
| 同一模型处理多种语言 | 促使参数复用，支持跨语言迁移 |
| 平行文本、翻译和双语页面 | 直接把两种表达关联起来 |
| 共享实体、代码、数字、标记和网络材料 | 提供跨语言锚点 |
| 相似任务和上下文结构 | 让模型学习可迁移的处理模式 |

因此，跨语言能力既不是只靠翻译对，也不是只靠单语数据自动出现。不同模型的数据配比和训练方法并不公开，不能用一个固定百分比解释所有系统。

## 为什么不能从输出判断“内部语言”

有些产品会展示英文的 reasoning 文本，或者在检索时生成英文查询。这最多说明产品的推理呈现、工具链或训练偏好使用了英语；它不能证明模型先在内部把每个中文问题翻成英文。反过来，模型直接输出中文，也不能证明所有中间表示都是“中文思维”。

对一个不可直接观察的内部状态，更可靠的判断是比较行为：跨语言迁移是否存在、翻译和原语言输入的误差如何变化、不同语言的 token 成本和检索资料是否改变结果。

## 语言能力为何不均衡

英语在许多公开语料、基准、开发资料和工具文档中占比很高，因而常具有更广的覆盖；但这个现象会随模型、领域和语言变化。更具体的限制包括：

- **训练覆盖**：低资源语言、专业术语或地方变体的样本可能较少；
- **token 效率**：同一段内容在不同 tokenizer 下消耗的 token 数不同，影响上下文容量和成本；
- **后训练与评测**：指令数据、偏好数据和安全评测若偏向某语言，行为会随之倾斜；
- **外部系统**：检索语料、工具接口和知识库的语言覆盖会影响整个应用，而不只是模型。

所以“英语一定更强”与“各语言已经没有差距”都不是可靠规则。

## Prompt 应怎样选择语言

先用用户和业务材料本来的语言写 prompt，并直接评测目标任务。若结果不稳定，可以把语言本身作为实验变量：

1. 使用原语言输入和输出；
2. 在保留原始资料的前提下测试双语指令；
3. 对确有价值的场景测试翻译后推理与回译；
4. 比较正确性、引用、延迟、token 成本与用户可读性。

英文 prompt 加中文输出有时会帮助某个模型、某类资料或某个历史版本；它不是普适的质量捷径。翻译步骤也可能丢失术语、歧义和地域语境。

## 小结

多语言 LLM 不是把每个输入机械翻译成英语再工作。它在多种 token 序列上训练并通过共享参数形成可迁移、但不完全统一的表示。语言选择是数据、tokenizer、模型和外部资料共同作用的工程变量；最可靠的结论来自对目标语言与目标任务的直接评测。
