# 大模型推理的不确定性：从采样到工程实现

同一段提示词、同一组模型参数和 `temperature=0`，为什么有时仍会得到不同结果？要回答它，必须把三个层次分开：解码是否随机、一次前向计算是否确定，以及一个在线推理服务是否会让单个请求遇到相同的计算条件。

这不是“模型忽然改变了想法”。通常是服务为了吞吐把请求放进不同批次、使用不同形状的算子或以不同方式切分序列；有限精度下，这些条件可能让很接近的 logits 交换顺序。自回归生成再把第一次差异带入后续上下文。

## 先区分：采样随机性与系统不确定性

模型先给出下一个 token 的 logits。解码器再决定怎样选 token：

- **采样**会按概率分布随机选择，因此同一输入可以有不同输出；
- **贪心解码**通常选择最大 logit；很多 API 把 `temperature=0` 实现为这一方式；
- **temperature、top-k、top-p**改变采样分布或候选集合，但是否随机还取决于是否真的采样。

因此，温度为零并不让模型“更不稳定”。它消除了有意的采样随机性；若输出仍不同，问题在于数值和服务运行条件，而不是采样器掷骰子。

## 为什么数值条件会影响 token

浮点加法不满足严格结合律。理论上：

$$
(a+b)+c=a+(b+c),
$$

但有限精度会在每一步舍入。并行计算常把归约组织成不同的树形顺序；不同顺序可能得到极小差异。

对固定硬件、软件、输入形状和计算路径，许多常用前向算子会稳定复现同一结果。问题在于线上服务中，“同一个用户请求”并不是完整输入：同批还有哪些请求、批次多大、Prefill 是否被切块、KV Cache 如何分页，都可能改变内核选择或归约布局。

```text
请求负载变化 → 批次/切分变化 → 有限精度 logits 微差
             → 临界位置的 argmax 改变 → 后续 token 自回归分叉
```

## Batch invariance：问题的关键边界

一个内核若具有 **batch invariance**，则某个样本的数值结果不应因为同批样本数量或位置改变而改变。Thinking Machines 的实验指出：许多 LLM 前向内核可以做到“同样的完整批次重复运行时确定”，却不一定对批次形状不变；在线服务的动态批处理因此会让单个用户从外部观察到不确定性。

这比“GPU 并行天然随机”更准确。GPU 并行和浮点舍入是条件；真正需要检查的是：服务是否让请求经历了会改变其数值路径的批次或分块条件。

在该研究的特定实现中，需要重点处理的归约类计算包括 RMSNorm、矩阵乘法和 Attention。它们不是所有推理系统里仅有的风险点，也不能据此推断任一 vLLM 或 TensorRT 部署必然不确定。

## 为什么微差会变成完全不同的回答

`argmax` 是从连续分数到离散 token 的边界。若前两个候选非常接近：

```text
logits A: [5.000000, 4.999999] → token 0
logits B: [4.999998, 4.999999] → token 1
```

差异本身很小，选择却不同。新 token 进入上下文后，下一步分布也会改变，最终文本可能显著分叉。反过来，若最大 logit 有足够大的间隔，同样级别的数值差异不会改变结果；不确定性不是每次请求都会出现。

## 怎样获得可复现的结果

目标要先说清楚：

| 目标 | 需要控制的条件 |
| --- | --- |
| 同一服务周期内结果稳定 | 固定解码、模型与 tokenizer，减少或消除批次/分块依赖的数值路径 |
| 离线实验可复现 | 记录权重、数据、随机种子、量化、硬件、驱动、运行时和服务配置 |
| 线上行为可追溯 | 保存请求版本、模型版本、解码参数、工具环境、结果与 trace |

批次不变的内核是其中一种方案。它要求每个样本在不同批次条件下采用一致的数值归约策略，通常会牺牲一部分动态调度或峰值性能。Thinking Machines 在特定 Qwen3-235B-A22B、提示词和部署实现的实验中报告：默认设置下 1,000 次贪心完成出现 80 个不同结果；启用其 batch-invariant 内核后，这 1,000 次完成一致。这个结果说明一种可行工程路径，不是对所有模型、硬件和服务的普遍性能承诺。

## 对训练和评测意味着什么

强化学习和严格评测需要区分“理论中的策略”和实际采样系统。若服务条件改变了贪心选择，采样分布可能偏离训练假设；这会给 on-policy 分析、回归比较和失败复现引入噪声。它不自动证明训练已经失效，也不能只用某个 KL 值证明整个系统完全一致。

实际工作中，先固定可控变量并记录不可控变量。只有当任务确实要求同一部署周期内的强确定性时，再评估批次不变内核、固定调度或确定性模式带来的性能代价。

## 小结

`temperature=0` 去掉的是有意采样随机性，不能单独保证线上输出一致。一次固定计算路径可以是确定的；面向单个用户的服务仍可能因动态批处理和有限精度而不确定。理解这条边界，才能把“模型随机”拆成可测量、可治理的解码、数值和服务问题。
