# 多模态模型：文字之外的信息怎样进入计算

前面的 LLM 主线是：文字被切成 token，Transformer 根据上下文预测下一个 token。多模态没有推翻这条主线，而是把模型的输入和输出从“只有文字”扩展为图片、音频、视频等多种信息形式。

多模态能力涉及三件相连的事：不同信号怎样变成可计算的表示；它们怎样和文字在同一次推理里组合；模型最后究竟能输出文字，还是也能生成图片、声音和视频。回答这些问题，才能区分“看见输入”“理解任务”和“生成结果”分别来自哪里。

## 多模态的全景：把不同信号接到同一计算中

文字、图片、音频和视频的原始形态完全不同：文字是离散符号，图片是像素阵列，音频是随时间变化的波形，视频则同时包含画面和时间顺序。它们不能原样混在一起交给 Transformer，必须先各自变成表示。

```text
输入                                                     输出

文字 ──→ Tokenizer / 文本 Embedding ──┐              ┌──→ 文本 token → 文字
图片 ──→ 视觉编码器 ──────────────────┤              │
音频 ──→ 音频编码器 ──────────────────┼→ 核心 Transformer ─┼──→ 音频 token / 声音解码器 → 声音
视频 ──→ 视频编码器 ──────────────────┤              │
                                      │              └──→ 图像/视频表示与解码器 → 图像/视频
                                      └→ 交错的多模态上下文
```

左边的编码器负责把原始信号变成一组向量或 token；中间的核心模型负责让这些表示互相影响；右边的输出头或解码器负责把计算结果变回某一种可交付的形式。图中的组件是职责划分，不要求每个产品都有完全相同的独立模块。

因此，“一个模型支持文字、图片、音频和视频”通常是指：这些模态的表示能够进入同一个上下文，让核心计算同时利用它们。它不意味着 JPEG 字节、声波和文字本来就是同一种 token，也不意味着模型一定会生成所有模态。

| 组件 | 它解决的问题 | 它不单独保证什么 |
| --- | --- | --- |
| 输入选择与切分 | 决定哪些图块、声音片段或视频帧进入计算 | 所有细节都会被保留 |
| 模态编码器 | 把像素、波形或帧变成一组向量表示 | 表示已经和问题、文字正确对应 |
| 连接与融合 | 让核心模型可以利用这些表示 | 模型已经正确理解画面或声音 |
| 输出头或解码器 | 把计算结果交付为文字、声音或图像 | 结果事实正确，或已经执行了动作 |

## 输入怎样进入同一上下文

用户可以把信息交错地提供给模型，例如先发一段文字，再附一张图片、一段录音和一段视频，最后继续提问。经过各自的编码步骤后，核心模型看到的可以抽象为：

```text
[文字 token] [图片的表示] [音频的表示] [视频帧的表示] [后续问题 token]
                                      │
                                      ▼
                            同一个 Transformer 上下文
```

图片常会先缩放、切成图块，再由视觉编码器产生一串视觉表示；音频会按时间分段；视频除了画面内容，还必须保留帧的先后和可能的音画同步。输入选择本身就在决定模型能看见什么：小字、短暂画面、说话人的语气或背景声，都可能在缩放、采样和压缩中被削弱。

这些非文本表示还需要通过连接器、投影层或跨注意力接口接入语言模型。实现可以不同：有的把视觉或音频表示作为一段额外 token 放进上下文，主要依靠 self-attention；有的在模型层内让文本状态查询模态表示。共同目的只有一个：**让问题中的文字和非文本线索在同一轮计算里彼此影响。**

也没有唯一的产品组织方式。编码器加连接器的路线通常让 LLM 接收多模态上下文并输出文字或结构化请求；统一离散 token 的路线可在一条自回归序列中处理多种模态；另一类系统让核心模型产生条件或隐藏状态，再交给专门的图像、语音或视频生成器。模块化路由、统一融合和外部工具可以同时存在，应由任务、时延、资料和可验证性决定，而不是把其中一种说成必然更高级。

这解释了“统一”真正意味着什么。统一的是后续计算中的上下文和任务，不是所有模态从一开始就使用相同的编码器，也不是所有模型都采用同一种连接方式。

## 监控截图的两条输入路径

用户发送一张监控面板截图，问“哪个服务的延迟突然升高”。系统不一定直接把图片接入多模态模型；它也可以先调用 OCR 或图像描述工具，把识别出的文字交给纯文本 LLM。

```text
路径一：截图 → OCR / 图像描述 → 文本 → 文本 LLM → 回答

路径二：截图 → 视觉表示 ────────┐
                               ├→ 多模态模型的后续计算 → 回答
        用户问题 → 文本表示 ─────┘
```

第一条路径把中间转写显式留下，便于审计和复用已有文本流程；但它可能丢掉曲线形状、颜色图例与空间位置。若 OCR 只给出“服务 A、服务 B、120 ms”，文本模型未必知道数值属于哪一条曲线。第二条路径有机会保留这些关系，却仍可能误认细小标签、遗漏区域或弄错对应关系。直接接收图像不是准确理解的保证。

## 一张截图怎样变成文字回答

对于直接接入视觉表示的路线，截图中的服务名、曲线、颜色图例和时间轴需要与问题一起参与计算。

截图中的服务名、曲线、颜色图例和时间轴先变成视觉表示；问题中的“哪个服务”“延迟”“突然升高”变成文本 token。二者进入同一上下文后，Transformer 可以让问题所表达的关系影响对图例、曲线和时间位置的利用。融合后的隐藏状态最终通过文本输出头，逐个预测“服务”“B”“在”“14:20”“后”等回答 token。

```text
截图 → 图块 → 视觉表示 ────────┐
                               ├→ [视觉表示 + 问题 token] → Transformer → 文本回答
问题 → token → 文本表示 ───────┘
```

关键在于：视觉编码器不会独自给出“服务 B 延迟升高”的结论；它提供线条、颜色、文字和位置等线索。LLM 也不是凭语言能力猜答案；它要在这些线索与问题之间建立对应关系。图例太小、曲线被遮挡、时间轴没有被正确利用时，模型仍可能生成流畅但错误的回答。

音频和视频遵循同一职责链。语音助手可以先将声音转写成文字，再生成文字回答，最后由语音合成读出；[Whisper](https://arxiv.org/abs/2212.04356)是音频到文本识别的一种实例。转写会让语言模型只看到文字：如果把“不要重启”漏成“重启”，后续推理便从错误前提出发。直接利用音频表示则有机会保留停顿、音调和环境声，但能否正确利用，仍取决于训练任务与输入采样。视频也是如此：帧选择过稀时，变化发生的瞬间可能根本没有进入计算。

## 输出能力分层：能理解，不等于能生成

输入和输出不对称。一个能看图、听音频、理解视频的模型，最常见的结果仍是输出文字或结构化数据；非文本输入只是回答的条件。

| 能力类型 | 输入 | 输出 | 需要增加什么 |
| --- | --- | --- | --- |
| 多模态理解 | 文字、图片，常也有音频和视频 | 文字或结构化结果 | 让非文本表示影响文本 token 的预测 |
| 多模态对话 | 多种交错输入 | 文字，也可能是声音 | 为语音等输出增加对应的 token 或解码路径 |
| 任意模态生成 | 多种交错输入 | 文字、图片、声音，部分还有视频 | 能表示、预测并解码每一种目标模态 |

若要生成声音、图片或视频，模型右侧还要有对应的输出表示和解码机制。一个路线是把这些模态离散化为 token，让核心模型像预测文字一样预测它们；[AnyGPT](https://arxiv.org/abs/2402.12226)和[Chameleon](https://arxiv.org/abs/2405.09818)展示了这类思路。另一条路线是由核心模型产生条件或隐藏状态，再交给专门的语音、图像或视频生成器；[Qwen2.5-Omni](https://arxiv.org/abs/2503.20215)展示了核心推理与语音输出模块协作的例子。

所以，一个产品对外表现为“文字、图像、视频和语音都能输入输出”，内部可能是联合训练的多模态模型，也可能是 LLM 与多个专门生成器组成的系统。判断原理时，应问：哪些表示进入了核心 Transformer，最后一种输出又由哪个模块产生。

## 训练怎样形成跨模态能力

把编码器、LLM 和输出模块连起来，不会自动产生多模态能力。训练至少要逐层解决“对应”“生成”和“行为”三个问题：

```text
配对或交错资料：图文、音文、视频文字、混合文档
        │
        ▼
学习不同模态的内容、位置和时间怎样对应
        │
        ▼
条件生成资料：给定若干输入模态，目标是文字或另一种模态
        │
        ▼
学习从哪些输入线索生成哪一种输出
        │
        ▼
指令、偏好、验证和安全信号
        │
        ▼
学习围绕用户任务组织输出，并限制不希望的行为
```

图文配对可以教会“这张图与这段描述有关”，但不等于模型会回答“异常从什么时候开始”。图像、问题和示范回答的训练，才会教它在面对具体问题时选择哪些视觉证据、怎样表达不确定性。[CLIP](https://arxiv.org/abs/2103.00020)说明了匹配式对齐，[LLaVA](https://arxiv.org/abs/2304.08485)则说明了视觉指令训练如何把图像和提问连接到回答。

若目标是生成图片、声音或视频，训练目标也必须包含相应模态的目标表示。离散 token 路线直接预测这些 token；专门生成器路线则让生成器在核心模型给出的条件下，用自己的生成目标学习。它们都不是把文本 Softmax 直接套到原始像素或声波上。

大型模型可以在文字、图像、音频和视频资料上联合预训练，再通过后训练改善对话和安全行为；[Gemini 技术报告](https://arxiv.org/abs/2312.11805)描述了这种组织。但“联合训练”不是万能答案：训练资料是否包含所需的跨模态关系、目标是否奖励正确利用这些关系、评测是否覆盖混合输入，仍然决定模型是否可靠。

## 多模态没有取消外部系统的边界

模型根据截图回答“服务 B 在 14:20 后延迟升高”，是在解释一次给定输入；它没有因此获得实时指标，也没有重启服务。进一步处理故障，还需要[LLM 与外部世界的交互链](../part3-llm-external/llm-external-interaction.md)提供查询、授权、执行和反馈。

即使任务看起来只是“点击屏幕上的重启按钮”，也仍有几个不同的环节：识别按钮、提出动作、由外部程序执行，再观察界面或服务状态。识别坐标正确不等于操作获准；界面出现提示也不一定证明服务已经恢复。

多模态扩展了模型可观察和可生成的信息形式，却没有自动带来实时性、事实正确性或执行权。把它放回全书的主线，可以记住：**编码器决定什么信号进入计算，核心模型决定这些信号怎样组合，输出模块决定它能交付什么，而外部系统决定它能否真正行动并验证结果。**
