# 推理服务的性能与容量：延迟、吞吐与 KV Cache 怎样互相制约

推理服务的性能问题通常以一句话出现：“首字很慢”“越聊越慢”“显存总是不够”或“明明每秒 token 很高，用户却在排队”。这些现象不能用一个 QPS 或 GPU 利用率解释。它们来自同一组约束：请求何时到达、输入和输出有多长、状态占了多少显存，以及调度器怎样让请求共享模型。

这一章只讨论已加载模型的在线推理。Transformer 架构定义模型要进行哪些计算；推理引擎负责在有限资源里安排这些计算。

## 先把“快”拆开

一次流式请求至少有四段时间：

```text
请求到达 ── 排队 ── Prefill ── 首个 token ── Decode ── 最后一个 token
              │                     │              │
           等待资源              TTFT 的组成      输出速度
```

- **排队延迟**：请求在真正执行前等待实例、显存或调度机会的时间。
- **首 token 时间（TTFT）**：从请求到达至用户看到第一个生成 token 的时间；它包含排队、输入处理和 Prefill。
- **每输出 token 时间（TPOT）**：相邻两个输出 token 之间的时间，近似描述持续生成的速度。
- **端到端延迟**：请求完成所花的总时间，受输出长度影响很大。

因此，“平均响应时间下降”不必意味着交互体验变好：把请求攒成更大的 batch，可能提高总吞吐，却让 TTFT 变长。离线摘要、批量抽取通常以吞吐和单位成本为主；对话、代码补全和语音交互通常先约束 TTFT 与 TPOT。服务目标应先写清楚，否则优化没有方向。

## 容量为什么不是 QPS

同样是每秒十个请求，十条短问答与十条带长文档、持续生成数千 token 的请求，对服务不是同一种负载。判断容量至少要同时看：

| 负载维度 | 它改变什么 |
| --- | --- |
| 到达速率与突发 | 队列是否持续增长，是否需要预留余量 |
| 输入 token 长度 | Prefill 工作量、首 token 时间和初始 KV 状态 |
| 输出 token 长度 | Decode 时间、连接持续时间和状态生命周期 |
| 上下文长度 | 每条活跃序列的 KV Cache 占用与可并发数 |
| 共享前缀与会话连续性 | 能否复用已计算状态，流量该路由到哪里 |
| 取消、超时和流式消费 | 无效生成能否及时停止并归还资源 |

显存先要容纳模型权重和运行时工作区，剩余部分才可留给活跃请求的 KV Cache。每条序列的缓存会随已处理的上下文和已生成的 token 增长；可同时服务多少请求因而是一个随长度分布变化的数，而不是固定并发值。设置最大输入、最大输出、并发上限和队列上限，是把这一不确定性变成明确服务契约。

## KV Cache：速度优化，也是容量约束

生成下一个 token 时，Attention 仍需读取此前 token 的 Key 和 Value。KV Cache 保存这些中间状态，使系统不必为每一步重新计算整个前缀；新 token 的 Query 仍然需要计算。它不是对话历史的业务记忆，也不会自行解决上下文过长的问题。

```text
同一请求：已处理 token 的 K/V ──保留──→ 下一步 Attention 复用
多个请求：相同前缀的 K/V ──命中──→ 跳过该前缀的重复 Prefill
```

第二种复用常被称为**前缀缓存**。多个请求确实拥有相同的系统指令、长文档或工具定义时，可以复用对应 KV 状态，减少重复 Prefill；文本看起来相似、顺序不同或只有部分未对齐时则未必命中。缓存的空间有限，需要选择保留、逐出或重新计算；跨租户共享还必须考虑隔离和时序泄露，不能把“命中率高”当成唯一目标。

把 KV 状态转移到主存、磁盘或其他机器，能暂时腾出昂贵显存，却增加传输和恢复等待。只有转移的代价低于重新计算或能够满足服务目标时才有意义。对大多数读者，关键判断不是某个引擎采用哪种分页算法，而是：状态在哪里、下一步何时需要它、搬运是否比重算更划算。

## 批处理怎样同时改善和伤害体验

模型权重很大。让多个请求共同执行，能分摊权重读取和设备启动开销，提高每秒处理的 token 数；但请求长度不同，固定 batch 容易被最长请求拖住。在线推理通常在生成步之间动态加入或移除序列，让短请求结束后立即释放其位置。

这不消除取舍。过于追求大 batch，短交互请求会等待；过于追求极低 TTFT，设备可能长期吃不满。调度策略应服从服务等级：可将交互、批处理和高优先级流量分开排队，限制单请求的输入与输出，允许已取消请求尽快停止 Decode，并持续观察队列长度和尾延迟。

## 长 Prefill 为什么会让“正在回答”的请求卡住

连续批处理解决了短请求结束后空位闲置的问题，却引入一个更细的取舍。一个新到的长文档请求需要很长的 Prefill；若调度器一次把它完整处理完，已经在 Decode 的对话必须等到这段输入计算结束，用户看到的输出就会突然停顿。

```text
不分块：  Decode ───────────── 等待长 Prefill ───────────── Decode
分块交错：Decode ── Prefill 一块 ── Decode ── Prefill 一块 ── Decode
```

**分块 Prefill** 把长输入切成若干段，在调度迭代之间穿插已有请求的 Decode。它不减少处理这份输入所需的总工作，反而可能因更多次启动和权重读取增加少量开销；它改变的是等待的形状：已有会话不必承受一次很长的输出间隔，新请求也能逐步离开队列。

块不应越小越好。块越大，长请求越早完成输入处理，却更容易破坏其他请求的 TPOT；块越小，流式输出更平稳，却增加调度和执行开销。合理的上限来自服务目标：先给正在生成的请求规定可接受的最长输出间隔，再在剩余时间内安排尽量大的 Prefill 块。这里的核心不是某个固定 token 数，而是让调度时间片服从交互体验。

| 现象 | 优先检查的因果链 |
| --- | --- |
| 首 token 变慢 | 突发排队、长输入 Prefill、共享前缀是否命中 |
| 首 token 正常、后续输出变慢 | Decode 的显存带宽、活跃序列数与批处理策略 |
| 显存不足或并发突然下降 | 权重与工作区占用、KV Cache、上下文和输出上限 |
| 总吞吐提高但交互体验变差 | batch 等待、队列隔离和 TTFT 目标是否被牺牲 |
| 扩容后效果不明显 | 新实例加载与预热时间、流量是否仍集中在旧实例 |

这些只是排查入口，不是固定处方。要用按请求长度、模型版本、优先级和时间段切分的指标验证判断；平均值经常掩盖长尾与突发。

## 显存紧张时，暂停不是免费的

KV Cache 随请求增长，而显存是有限的。引擎可以为每条请求预先留出最大长度的空间，但大量请求提前结束时会浪费容量；也可以按 token 增长逐步分配固定大小的 KV 块。后一种方法使同一序列的逻辑顺序与物理存放位置分离，减少连续大块预留带来的碎片。它是推理状态的分配策略，不是另一种 Attention 算法。

内存耗尽时，调度器还可能**抢占**一个请求：暂停它，释放其私有 KV 状态，随后再恢复。恢复路径有三种，代价依次不同：

| 恢复方式 | 节省什么 | 付出的代价 |
| --- | --- | --- |
| 状态仍在本地显存 | 几乎不需要恢复 | 长期占用最稀缺的容量 |
| 从较慢存储取回状态 | 释放部分显存 | 传输延迟与带宽竞争 |
| 根据输入和已生成内容重新 Prefill | 不保留 KV 状态 | 重算时间、TTFT 或后续输出停顿 |

抢占不是“免费把并发变大”。它只是把内存压力转换成恢复成本，并可能让被抢占请求的尾延迟变差。是否抢占应取决于优先级、预计等待时间、状态大小、可否取消以及恢复后是否仍能满足时限；对正在流式交互的请求，频繁抢占往往比拒绝或排队更糟。

## 何时值得拆开 Prefill 与 Decode

长输入主要把压力放在 Prefill，长输出和大量并发会持续占用 Decode 及 KV 状态。某些高负载系统会为两阶段分别配置资源池：Prefill 完成后把 KV 状态交给 Decode 池继续生成。

```text
长上下文请求 → Prefill 池 ──传递 KV 状态──→ Decode 池 → 流式输出
```

这种 **Prefill/Decode 分离** 能让两类资源按不同负载扩展，也避免长 Prefill 长时间干扰已有流式生成；代价是状态传输、更多路由逻辑和新的故障边界。输入短、流量小或单机已经满足目标时，分离通常只会增加复杂度。它是为明确瓶颈服务的架构选择，而不是推理服务的必经形态。

## 推测解码：用并行提议减少串行步骤

Decode 的限制在于目标模型一次只确定下一个 token。**推测解码**让一个较快的草稿模型或草稿机制先提出连续多个 token，再由目标模型一次验证这一段：连续正确的前缀直接接受，首次不一致处由目标模型接管并继续。

```text
草稿：          a ─ b ─ c ─ d
目标模型验证：   a ─ b ─ c ─ ×
输出：          接受 a、b、c；由目标模型决定后续 token
```

它试图用一次较大的验证计算换取多个输出 token，从而减少用户等待的串行轮次。在采用正确的验证和采样规则时，最终仍以目标模型的分布为准；草稿只是在猜测目标模型可能接受的前缀。收益取决于草稿足够快、接受率足够高，以及验证工作没有挤占本就紧张的显存和 batch。草稿常错、目标模型本身很快、或系统已被其他请求压满时，额外的草稿工作可能没有收益。

## 用工作负载而不是峰值指标做决定

容量规划的输入应是目标模型、真实或保守的输入输出长度分布、突发到达方式、TTFT/TPOT/完成时间目标、可接受的降级策略和故障余量。先在这些条件下压测，再决定模型规格、实例数、缓存预算、队列规则和扩容阈值。原始 token 吞吐不等于服务能力：真正有价值的是在质量、时限与成本约束下完成的工作；为了提高每秒 token 而让大量交互请求超时，并不构成有效容量。

性能问题最终都能回到一个问题：有限的计算、带宽和状态空间，正被哪一种请求占用。把时间拆成排队、Prefill 与 Decode，把内存拆成权重、工作区与 KV 状态，把流量拆成长度和优先级，才有可能做出可解释的性能决策。
