# LLM 基础设施：模型怎样成为可靠服务

模型服务面对的不是一次孤立计算，而是长度、优先级和成本目标各不相同的请求流。第四部分关心：同一个模型怎样被很多人稳定地调用，并在延迟、成本、容量和可靠性之间取得可交付的平衡。

AI Infra 不等于购买 GPU。它包含计算设备、显存与存储、网络，以及把这些资源组织为训练和推理服务的软件。对本书的后端读者，最有用的入口不是先背硬件名词，而是沿一次请求追问：数据在哪里、状态在哪里、谁在等待、哪一种资源成为瓶颈、出错后如何恢复。

```text
用户 / 应用
    │ 请求、上下文、模型选择
    ▼
网关与路由 ──→ 推理服务 ──→ GPU / NPU 上的模型计算
    │                 │               │
    │                 │               └── 权重、KV Cache、显存带宽
    │                 ▼
    │           批处理与调度
    ▼
流式输出、指标、日志、限额与计费
```

模型本身定义要做什么计算；基础设施决定这些计算能否装入资源、如何与其他请求共享、何时返回以及怎样被观察。Agent 的工具循环属于第三部分；这里的循环是一次模型调用在服务系统中的排队、执行和交付。

## 从任务到资源：六层视角

一次模型服务跨越六层。它们不是产品必须划分的六个组件，而是一种定位瓶颈的办法。

| 层次 | 关心的问题 |
| --- | --- |
| 应用与任务 | 需要多快、允许多贵、是否流式、是否允许降级 |
| 模型与负载 | 模型大小、输入输出 token、上下文长度和并发到达方式 |
| 推理/训练系统 | 模型加载、批处理、KV Cache、请求调度和故障恢复 |
| 算子与运行时 | Attention、矩阵乘法等计算怎样映射到设备 |
| 处理器与存储 | 算力、显存容量、带宽和数据移动是否匹配 |
| 互联与集群 | 多卡、多机怎样交换张量、分配工作并隔离故障 |

因此，“接口慢”不是一个足够的诊断。可能是长输入导致 Prefill 很久，逐 token Decode 限制了首字之后的速度，KV Cache 挤满显存降低并发，排队在等待可用实例，或多机通信成为瓶颈。先确定在哪一层等待，才知道应该改 prompt、模型、调度、硬件，还是服务契约。

## 为什么它不像普通的负载均衡

传统 Web 服务常把一个请求分给一台有完整处理能力的实例；负载均衡的首要任务是把请求分散到健康、空闲的副本。请求当然仍可能访问数据库、缓存或其他服务，但应用计算通常无需让多台机器在同一条关键路径上同步完成一个步骤。

LLM 服务可以采用同样的形态：模型与其运行状态放得进一组设备时，多个完整副本分别服务不同请求，路由器主要做负载均衡和高可用。复杂性来自另一种情况：模型权重、KV Cache 或延迟目标超出单卡、单机的容量与带宽预算。此时，同一请求可能需要多个设备协作；每一层计算或每次生成都可能等待跨设备通信。

```text
典型 Web 服务：
请求 ──→ 负载均衡 ──→ 一个完整应用实例 ──→ 数据库 / 缓存 ──→ 返回

需要拆分的 LLM 服务：
请求 ──→ 路由 ──→ 一个推理实例
                         ├── GPU 0：一部分权重 / 状态
                         ├── GPU 1：一部分权重 / 状态
                         └── GPU n：一部分权重 / 状态
                                  │
                         在关键路径交换张量或状态
```

这不是说每个 LLM 请求都必须跨机器，也不是说传统系统没有分布式问题。差别在于调度对象下沉了：除了“哪个请求去哪个实例”，系统还可能要安排 Prefill 与 Decode、batch 中的 token、KV Cache block、模型分片、设备间通信和状态所在位置。KV Cache 还让服务带有状态亲和性：把后续请求送回缓存所在处可以省去重算，但会与均衡负载、故障切换和租户隔离发生取舍。

因此，硬件拓扑不是可以完全忽略的实现细节。更好的软件抽象能隐藏大量复杂性，却不能消除模型必须装得下、状态必须及时读到、分片必须同步这些物理约束。高性能部署仍需理解显存层次、设备互联和通信路径，如同高性能数据库仍需理解存储与索引。

## 谁在做“类似操作系统”的工作

把这些资源组织起来的过程很像面向模型负载的分布式运行时：它要调度工作、管理内存状态、提交设备任务、协调通信、隔离租户并从故障中恢复。但它不是一个统一的分布式操作系统；职责分散在多层，各自只管理一段范围。

| 类似 OS 的职责 | LLM 基础设施中的主要承担者 | 管理的对象 |
| --- | --- | --- |
| 请求与短期状态调度 | 推理引擎 | 队列、batch、Prefill/Decode、KV Cache、取消与流式输出 |
| 长期训练任务推进 | 训练框架与训练引擎 | 并行策略、梯度同步、优化器状态、checkpoint |
| 设备执行与通信 | GPU/NPU 运行时、驱动与通信库 | kernel、显存分配、stream、跨设备 collective |
| 资源放置与隔离 | 集群调度器与平台 | 机器、加速器配额、作业放置、容器与故障迁移 |
| 服务目标与生命周期 | 网关、路由和服务控制面 | 模型版本、流量、扩缩容、限额、观测与回退 |

推理引擎是离一次生成最近的“运行时”：它决定请求何时运行、怎样共享权重和显存、状态何时保留或释放。训练引擎处理的是另一类长期、同步的计算；集群调度器决定哪些机器与设备交给哪个任务；服务控制面再把模型能力交付给用户。它们共同构成系统，却不能互相替代。

### 一个 token 到底由谁负责？

Transformer 定义“算什么”：Q、K、V、Attention、FFN 和下一层的依赖关系。推理引擎决定“何时、和谁一起、以什么软件策略算”：请求是否排队、怎样组成 batch、KV Cache 怎样分配、调用哪个算子实现、是否拆到多张卡。硬件决定“用什么物理资源算”：矩阵在哪个计算单元执行、权重从哪级内存读取、设备之间经哪条链路传输。

```text
Transformer：定义计算图和数据依赖
推理引擎：组织请求、状态和执行策略
硬件/互联：提供计算、存储和数据搬移能力
```

KV Cache 的 K/V 来自 Transformer 的 Attention；KV Cache 怎样分页、共享、换出或释放，属于推理引擎；它究竟放在 HBM、主存还是跨设备传输，则受硬件与运行时约束。

### 推理引擎并非完全脱离模型

请求队列、batch、显存池、KV Cache 分配和流式输出对许多 Transformer 变体都可复用；但推理引擎仍要知道模型怎样计算 Attention、FFN、MoE 或其他特殊结构。模型配置描述层数、维度和架构类型，权重保存参数数值；它们本身不是可自动执行任意结构的程序。引擎通常以通用运行时配合架构实现或适配层，按配置构建计算并加载权重。

```text
模型配置：描述结构参数
模型权重：保存参数数值
推理引擎：架构适配 + 通用调度、缓存与硬件执行
```

所以“推理引擎”不是 Transformer，也不是与模型完全无关的普通服务器。它在模型计算图与设备资源之间建立了执行层；新的模型结构有时需要相应的引擎适配、算子实现或状态管理方式。

## 一次生成请求：Prefill、Decode 与状态

应用将系统指令、用户输入、检索资料和工具结果组成上下文，路由器选择一个具有目标模型和足够容量的推理实例。文本先 token 化，然后推理分为两个性质不同的阶段：

```text
上下文 token ──→ Prefill：并行处理已有输入，建立 K/V 状态
                                      │
                                      ▼
                         Decode：生成一个 token，追加状态，再生成下一个
```

**Prefill** 处理整段已有上下文，通常有较大的矩阵计算并行度；输入越长，计算和所需状态越多。**Decode** 每次只新增一个 token，后一步依赖前一步，天然更接近串行过程。在常见的大模型服务负载中，Prefill 往往更受矩阵计算吞吐约束，Decode 则需要反复读取权重和 KV 状态，往往更受显存带宽约束；具体瓶颈仍取决于模型、batch、上下文长度和硬件。用户感受到的延迟至少应拆成排队时间、首 token 时间和后续 token 速度；只报一个“平均响应时间”会掩盖不同问题。

吞吐与延迟也不是同一件事。把更多请求组成 batch 往往能让设备更充分读取同一份权重、提高每秒 token 数，却可能让单个用户先等更久。服务至少应分别观察：**排队延迟**（资源何时可用）、**首 token 延迟**（排队与 Prefill 后的首次可见结果）、**每 token 延迟**（Decode 的持续速度）和**端到端延迟**（完整交付时间）。交互式对话通常先关心首 token 和每 token；离线批处理更可能优先总吞吐与单位成本。

KV Cache 保存已经处理过 token 的注意力 Key 和 Value，避免每次生成都重算整个前缀。它节省计算，却会随层数、隐藏维度和上下文长度增长而占用显存。长上下文因此不只是“多算一点”：它还可能减少可同时服务的活跃序列，迫使系统排队、换出状态或限制长度。KV Cache 是一次推理的计算复用，不是应用选择保存的长期记忆。

## 为什么强算力不一定带来低延迟

模型执行同时受计算和数据移动限制。粗略地说：

$$
\text{time} \geq \max(\frac{\text{operations}}{\text{compute rate}},\; \frac{\text{bytes moved}}{\text{memory/network bandwidth}})
$$

矩阵计算量很大时，设备算力可能是瓶颈；逐 token Decode 常需要反复读取大量权重和状态，可能更受显存带宽限制。模型跨卡或跨机器时，还要等待通信。这个判断解释了常见优化为何方向不同：量化或更小模型减少权重与算力；批处理让多个请求共享权重读取；算子融合减少中间数据移动；更快互联减少并行计算的等待。没有测量就不能假定“GPU 利用率低”或“算力不够”是原因。延迟、吞吐与 KV Cache 的具体关系见《推理服务的性能与容量》。

## 并发、批处理与调度：共享资源也会互相等待

在线服务面对的不是一个请求，而是长度、优先级和生成速度不同的请求流。调度器需要在等待足够请求以提高设备利用率，与尽快开始以降低用户等待之间取舍。

**批处理**把多个请求一起送入设备，常能提高吞吐；但传统固定 batch 会被最长序列拖住。推理系统通常会在生成步之间加入或移除请求，使不同长度的序列共享计算。这样能提高利用率，却要同时管理每条序列的 KV Cache 和输出流。

容量不是单一 QPS。它取决于模型权重能否驻留显存、每个活跃序列占多少 KV Cache、输入输出长度分布、批处理策略和目标服务等级。限流、队列、优先级、最大上下文和最大输出长度都不是“体验细节”，而是让有限资源不被少数超长请求耗尽的服务控制。

## 从一张卡到集群：什么时候需要分布式

若模型权重和运行状态能放进一张设备，单机通常最简单，通信和故障面也更小。模型太大、吞吐目标太高或需要高可用时，才需要多卡、多机和多个副本。

| 扩展方式 | 主要解决什么 | 新的代价 |
| --- | --- | --- |
| 复制模型副本 | 服务更多独立请求、容错 | 权重重复占用资源，流量须路由 |
| 在多卡拆分一个模型 | 单卡放不下模型或状态 | 每步需要设备间通信 |
| 跨机器拆分 | 单机资源仍不足 | 网络延迟、带宽、拥塞与故障更突出 |

训练与推理都可能分布式，但负载不同。训练需要前向、反向和参数同步，重视大规模吞吐与 checkpoint；在线推理重视首 token、逐 token 延迟、KV Cache 和请求波动。不能把一种训练并行策略直接当成在线服务的答案。

## 服务治理：把模型版本变成可交付承诺

模型服务不仅是 HTTP 接口。一次可复现的行为由模型权重与版本、tokenizer、系统提示、工具 schema、检索索引、采样配置和路由策略共同决定。上线新模型时，需要逐步流量、回滚条件和与基线可比较的评测；否则出现质量或成本回归时，很难知道是哪一层变化。

可观测性也要沿请求链路建立：请求量和队列、首 token 与生成速度、错误和取消、活跃 KV Cache、设备显存和利用率、工具/检索带来的输入长度，以及每次请求的 token 和成本。指标帮助发现问题，轨迹和日志帮助解释问题；日志同时需要脱敏、访问控制和保留策略，不能为了可观测性把用户上下文暴露出去。

部署位置是延迟、数据边界、可用硬件和运维能力的共同选择。端侧可减少网络往返并保护部分数据，但资源有限；边缘可接近用户；云端便于使用大模型和弹性集群。没有普遍最优位置，必须从任务的时延、隐私、可用性、模型大小和成本约束反推。路由、扩缩容和上线治理如何把这些约束落实为服务控制面，见《推理服务的控制面》。

把全章压缩成一条因果链：任务决定服务目标和负载；输入长度决定 Prefill 与状态；生成长度决定 Decode 时间；状态和权重决定显存容量；并发调度决定等待与吞吐；设备、存储和网络决定每步数据能否及时到达；版本、观测和回滚决定服务能否长期交付。AI Infra 的本质，是让这些相互制约的条件成为可测量、可控制、可演进的系统。
