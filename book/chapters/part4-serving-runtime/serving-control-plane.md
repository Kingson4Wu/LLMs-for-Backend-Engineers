# 推理服务的控制面：路由、扩缩容与可靠交付

推理引擎负责让一台或一组设备执行模型；它不自动决定哪个请求应使用哪个模型、何时拒绝超载流量、何时启动新副本，或新版本出问题时怎样回退。这些决策构成**服务控制面**。它把模型计算包装成有目标、有边界、可运营的服务。

控制面不等于某个网关或 Kubernetes 产品。它是一组职责：识别请求需求，选择可用执行资源，限制不可承受的工作，改变资源规模，并以版本、指标和恢复机制维持服务承诺。

## 数据面与控制面各做什么

可以把在线服务区分为两条协作链路：

```text
请求 ──→ 网关 / 路由 ──→ 队列与策略 ──→ 推理引擎 / 模型副本 ──→ 流式响应
             │                 │                    │
             └──── 控制面：选择、限额、扩缩容、发布、观测 ────┘

数据面：执行 token 化、Prefill、Decode、KV Cache 管理和输出。
控制面：为这次执行选择模型和资源，并管理长期的容量与版本状态。
```

边界并不总以进程划分：一个小服务可以在同一程序完成全部职责，大型平台则会拆成网关、调度器、模型服务器和集群管理器。重要的是不要混淆：模型服务器的吞吐优化，不能替代流量隔离、发布策略或配额管理。

还要区分两种时间尺度。**集群调度器**决定一组机器和加速器给哪个模型服务或训练作业，关注资源放置、配额与故障域，变化通常以秒到分钟计。**推理调度器**在已经获得的设备组内，决定哪个请求、哪个 batch、哪个 Decode 步先执行，管理 KV Cache，变化以毫秒级迭代计。前者不能代替后者：即使集群分配了足够 GPU，推理引擎仍必须处理长度不同、状态不同的在线请求。

## 路由不是随机挑一台机器

一次路由至少要满足模型与能力匹配：请求所需的模型版本、模态、上下文长度、适配器或安全策略，必须由目标实例支持。随后才是在可用实例间选择：

| 路由信号 | 目的 |
| --- | --- |
| 队列、活跃序列与剩余 KV 空间 | 避开没有执行容量的实例 |
| 模型、版本和硬件能力 | 保证请求能正确执行 |
| 优先级、租户配额和成本策略 | 保护关键流量，避免少数用户耗尽资源 |
| 会话、共享前缀或缓存位置 | 减少状态迁移与重复 Prefill |
| 地域、数据边界和可用区 | 满足延迟、合规与故障隔离要求 |

只按 CPU 或 GPU 平均利用率路由，常会错过真正压力：一台设备可能计算利用率不高，却已被长上下文的 KV Cache 填满；另一台刚加载模型，尚不能立刻服务。路由需要使用与推理工作负载相符的状态，而不是套用普通无状态 Web 服务的假设。

### 有缓存时，到底该把请求送到哪里

对于带长上下文、多轮对话或固定工具定义的服务，路由器常常要在三条路径中选择：

| 路径 | 适合的条件 | 主要代价 |
| --- | --- | --- |
| 路由到本地命中缓存的实例 | 命中节省的 Prefill 大于额外排队 | 可能牺牲负载均衡 |
| 把状态传给更空闲的实例 | 状态较小或互联足够快 | 传输占用网络，增加故障边界 |
| 路由到空闲实例并重新 Prefill | 重算比等待或搬运更快，或不宜共享状态 | 重复计算与更高 TTFT |

不存在永远正确的缓存亲和性。缓存命中应与队列时间、状态大小、网络路径、租户隔离和故障恢复一起比较。把会话永久绑定在某台机器会降低弹性；完全忽略缓存位置又会让长前缀被反复计算。状态感知路由的目标是在这些代价之间作可测量的取舍。

## 服务单元怎样组织

控制面不只管理“有多少台机器”，还要明确一个可路由的服务单元是什么。常见形态有三种：

| 形态 | 请求怎样执行 | 适合什么 | 主要代价 |
| --- | --- | --- | --- |
| 完整副本 | 一组设备保存完整模型，独立处理请求 | 模型能放进单机或固定设备组，需要水平扩展 | 权重会重复驻留，缓存可能分散 |
| 分片推理实例 | 多卡或多机共同保存一个模型，协作完成同一请求 | 单卡放不下模型或单请求需要更大资源 | 每步通信进入关键路径，故障与拓扑更敏感 |
| 阶段资源池 | Prefill 与 Decode 分别由不同实例池执行 | 长输入与持续生成的负载差异明显 | 必须交接 KV 状态并协调两个池的容量 |

这三种形态可以组合：一个服务可拥有多个完整副本，每个副本内部又由多卡组成；只有在测得长 Prefill 与 Decode 相互干扰时，才值得增加阶段池。控制面需要知道这些边界，才能把“扩容一个副本”“扩大一个设备组”和“增加某阶段容量”当成不同动作，而不是同一种扩容。

## 扩缩容为什么比 Web 服务更慢

普通无状态副本启动后很快就能接请求；模型副本需要拉取权重、初始化运行时、分配显存，有时还要预热或建立缓存。扩容的有效时间因此可能远长于创建一个进程。若只在队列已经很长时才触发扩容，用户仍会经历一段长等待。

```text
负载上升 → 观察窗口确认 → 分配设备 → 加载与预热模型 → 健康检查 → 接入流量
```

有效的容量策略会同时设置：常驻基线容量、面向突发的队列和限流、扩容触发条件、加载期间的降级或备用模型，以及缩容时的排空规则。缩容不能直接杀掉正在生成的副本；应停止分配新请求，等待或按约定取消旧请求，并释放其 KV 状态。高可用也不只是更多副本：副本、路由器和依赖服务需要避免共享同一个故障域。

## 发布、回退与可复现行为

用户收到的结果不只由权重决定。模型版本、tokenizer、提示词模板、工具 schema、检索索引、采样参数、推理引擎版本与路由规则共同构成一次可交付行为。改变其中任何一项，都可能改变质量、延迟、成本或安全边界。

因此发布应先定义比较对象与停止条件，再逐步扩大流量：

```text
候选配置 ── 离线评测 ── 小流量观察 ── 扩大流量 ── 全量
                     │                     │
                     └── 质量、错误、TTFT、成本越界 → 回退
```

回退必须包含与新版本相同粒度的配置，而不是只把模型权重换回去。对于有会话和缓存的系统，还要决定旧会话如何继续、缓存能否复用、以及正在执行的请求是否保持原版本。没有这些边界，“一键回滚”只是一个不完整的承诺。

## 超载与故障时，优先保护什么

请求超时、客户端断开、工具链路失败和实例故障都会发生。可靠服务的第一步不是无限重试，而是分辨请求是否仍有价值、是否可能已经执行、以及重试会不会放大负载。

| 情况 | 应关注的控制点 |
| --- | --- |
| 客户端取消或连接断开 | 尽快停止 Decode、释放 KV Cache 与配额 |
| 队列持续增长 | 限流、排队上限、优先级、降级或快速失败 |
| 实例失效 | 健康检查、停止路由、重试边界与剩余容量 |
| 下游依赖变慢 | 总超时预算、熔断与隔离，避免占住模型资源等待 |
| 发布后质量或成本回归 | 可比较指标、流量闸门与完整配置回退 |

生成请求尤其不能盲目重试：同一语义请求可能生成不同文本，带工具调用的请求还可能造成重复副作用。是否重试必须由幂等键、执行阶段和业务语义决定。超时也不是单一数字；排队、模型生成和下游调用应共享一个明确的总时间预算。

## 可观测性让控制成为可能

控制面依赖可观察的状态。至少需要按模型、版本、租户、长度区间和优先级分组观察请求量、拒绝率、队列、TTFT、TPOT、完成时间、活跃序列、KV Cache、显存、取消、错误和 token 成本。平均值不足以说明交互体验，应同时看高分位延迟和突发时的行为。

指标告诉系统何时偏离目标；链路追踪解释一条请求经过哪些组件；日志帮助复原错误，但输入上下文和输出通常含敏感数据，必须脱敏、最小化保存并限制访问。把所有 prompt 原样记录下来，并不等于更可靠的观测。

推理服务的控制面持续回答三个问题：此刻该让谁执行、资源不足时先保护谁、改变配置后怎样知道服务仍满足承诺。把这三件事做好，模型计算才会成为可以长期运营的产品能力。
