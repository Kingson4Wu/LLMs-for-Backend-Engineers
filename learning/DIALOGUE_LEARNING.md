# 对话学习原则

这本书不是术语表或实现百科。对话的目标是帮助读者形成能用于工程判断的整体模型：模型接收什么信息，经过什么计算或系统边界，产生什么结果，以及哪些条件会让结论不成立。

## 解释一个问题时

先确定它位于哪一层：数学与学习、模型架构、训练过程、推理运行时、外部系统或服务基础设施。随后按需要说明：

1. 当前问题和它解决的限制；
2. 输入、处理与输出怎样连接；
3. 关键约束为何导致这种设计；
4. 它没有解决什么，以及与相邻概念怎样分工。

只在细节会改变因果理解或工程判断时展开公式、数据流或实现机制。不要把常见配置说成唯一解，也不要用类比替代机制。

## 两种对话方式

**问题驱动**从读者的真实任务出发。先把问题映射到 `BOOK_MAP.md` 中的环节，说明涉及的概念和边界，再根据读者已有经验决定从全景、机制还是案例切入。需要时用一个反例、取舍问题或简短复述检验理解。

**路径驱动**从读者的目标与前置知识出发。先给出可调整的路径和每一段解决的问题；每完成一个关键环节，再通过读者自己的工程场景检查是否能把概念说清。它不是固定课程，也不应为了“走完章节”而跳过读者真正的问题。

## 回到可核对的材料

讨论本书内容时，指出对应的章节 ID、标题或文件路径。原文与当前书稿不一致时，以 `../book/` 的中文源稿为准；英文是独立镜像，应避免把其简略表述当作中文原文的完整替代。

将回答分清三类：

| 类型 | 处理方式 |
| --- | --- |
| 书中已有的结论 | 指向章节并按原文的因果链解释 |
| 基于书中机制的推导 | 标明前提，说明为何能推出该判断 |
| 会随模型、产品、论文或行业实践变化的事实 | 查阅可靠的一手资料，并说明时间和适用范围 |

当读者问到书外的实现、产品或最新结论时，可以扩展讨论，但应先说明它与书中哪一层相连，不把短期工具细节伪装成稳定原理。

## 面向后端工程师的连接方式

可借用熟悉的系统经验来解释职责和约束，例如：请求生命周期、状态复用、缓存命中、队列、调度、事务、权限、观测和回归测试。但类比只用于定位对应关系；模型计算、概率生成和训练优化仍须按自身机制说明。

好的结束方式不是重复结论，而是让读者能回答一个具体判断：在什么条件下应使用这项机制，它带来什么代价，失败时应到哪一层寻找原因。
