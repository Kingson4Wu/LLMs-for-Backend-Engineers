# LLM 服务运行载体设计

## 目标

新增第四部分“LLM 的运行载体：从一次调用到可交付服务”。它面向后端工程师，解释一次模型调用怎样成为可交付、可观测的服务，并保持本书“先建立全局地图，只在决定工程判断的地方进入必要细节”的边界。

## 读者应带走的模型

读者能够区分两类运行时：第三部分的 Agent 运行时负责目标、状态、工具与权限；第四部分的模型服务运行时负责请求排队、模型执行、状态驻留与输出交付。读者也能够把用户可见的等待拆成排队、首 token 和持续生成，并理解上下文长度、输出长度、并发与部署位置如何共同影响体验和成本。

## 结构

第四部分按一个请求的生命周期组织：

1. **一次调用怎样成为模型服务**：应用组装输入、路由、分词、排队、Prefill、Decode、流式交付；建立从任务层到计算资源层的四层地图。
2. **延迟、吞吐与状态**：区分 TTFT、输出 token 间隔和端到端时间；区分模型权重、KV Cache 与临时计算状态；说明长上下文、长输出与并发的约束。
3. **调度、缓存与容量**：用队列、批处理、准入和缓存复用解释为何服务能同时推进请求，也解释等待、容量与成本的权衡。
4. **部署位置与服务闭环**：以数据边界、网络、容量、可靠性和更新节奏选择本地、边缘或云；区分应用指标和模型服务指标。

## 全局导览与边界

第一章包含一张四层地图：任务与应用、模型请求、模型服务运行时、计算与网络资源。加速器、网络、分布式并行和训练集群只作为最下一层的能力来源出现；正文不解释其内部机制。需要这些知识时，读者转向《深入理解 AI Infra》或官方实现资料。

本部分不重复第二部分已有的 Token、注意力、Prefill、Decode 与 KV Cache 机制，而是链接到主解释处，并补充它们在服务端的后果。它不介绍某一推理框架、硬件型号、内核优化、性能数字或部署脚本。

## 事实边界

- Prefill 和 Decode 描述常见自回归生成服务，不能写成所有模型任务的统一阶段。
- 批处理常可提高资源利用率，但不保证单个请求更快；结果依赖工作负载和服务目标。
- KV Cache、跨请求前缀复用和应用长期记忆必须分开。
- 本地、边缘、云没有绝对优劣，选择应由数据位置、网络、容量、可靠性和运维条件决定。
- Agent 任务的总耗时还包括工具、外部系统与人工审批等待，不能归因于模型生成。
